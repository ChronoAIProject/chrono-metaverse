# 第 7 章 写回与上线

本地做好的物件集要变成时间线上的一次提交：**打包 → 检查 → 推送成重建草稿 → 人看预览 → 发布 → 验证**。演示空间另走部署种子。
规则的权威是[服务端瘦身定稿](../design/server-slim.md)第 2、3、6、7 节和 [SHAPES](../SHAPES.md) 第 7、8 节。

## 7.1 打包

```bash
metaverse-recon bundle --authored out/authored/authored.json --webmodel <网页用模型.glb>
# 不用物件集、直接用基线里的算法结构和物体：metaverse-recon bundle --algorithm
```

`bundle` 依次做：外部模型下载、核对并重新导出成物件模型 glb（`models`：摆放和调色烘进网格、节点单位变换、原点在底面中心、按上限减面
和缩小贴图）；外链贴图和本地贴图文件收进包；烘焙（`bake`）；逐件偏差（`fit`）；按类别建议锚点；网页用模型（`--webmodel` 给了就用它，
否则生成）；扫描打包（`scan-zip`）；最后调用 `metaverse bundle check`。输出：

```
out/bundle/
  manifest.json              清单：格式和版本、生成工具、说明、基础版本 base、扫描、重建层、锚点、文件表
  scan/scan.zip              原始扫描（本地可以没有：线上已有时推送会按哈希复用）
  web/scan-0.glb             网页用模型（默认档）
  models/<哈希前 12 位>.glb   物件模型
  textures/<哈希前 12 位>.jpg 贴图（烘焙、结构、材质库、扫描提取、AI 生成的）
  notes.md                   建模过程记录（提交的建模记录，不公开）
```

几条规矩（服务端按这些展开，违反了推不上去）：

- **重建层的编号以 `rb.` 开头**：`bundle` 自动加，模板引用一起改；扩展层不能用这个前缀。锚点编号不变。
- **整体替换**：`rebuilt.mode: "replace"`——发布后重建层整体换成这一份（先清空、再放），扩展层的修改原样保留。清单也支持逐件合并
  （`"merge"`：只放、改列出的物件，再删 `remove` 里的编号，不存在的跳过），只改几件时用；前厅各版一律整体替换。
- **锚点只新建、不覆盖**：同编号的锚点已经存在或**曾经存在过**，都跳过。所以重推不会多写，被人删掉的锚点也不会被包重新建出来。
- **基础版本** `base` 取打包时工作区的 `{spaceId, seq}`；推送和发布按它查冲突（7.3 节）。
- **不要手改 `out/bundle/`**：清单里每个文件都有大小和 sha256，改了就过不了检查。要改就改物件集、重新打包。
- **清单不写任何下载地址、不含本地路径**：同一个包在本地、推送和种子里是同一份字节、同一个哈希。
- 包里没有方块（重建包第一版不带方块化）。

## 7.2 检查和推送

```bash
metaverse bundle check          # 清单的全部规则、本地文件的大小和 sha256、glb / 图片 / zip 的内容、只有模型的物件与模型包围盒一致
metaverse bundle push           # 默认读 out/bundle/
```

`bundle push` 做：

1. 再跑一遍检查，不过就停；
2. 核对基础版本：清单没有 `base` 时拒绝（除非 `--base latest`，会警告"冲突检查只覆盖从现在起的变化"）；`base.spaceId` 和工作区的空间
   不同就拒绝；时间线已经前进时提示"发布时会检查冲突"；包的扫描和线上相同、变换却不同时提示（重扫要先对齐）；
3. 经重建路径逐个上传文件（同时 4 个）：**空间里已有、核对结果合乎用途的直接复用**，不传数据；本地没有又不能复用就停下报错
   （通常是原始扫描，先 `metaverse pull --scan`）；其余分片上传、等服务端核对；
4. 上传清单，建重建草稿，交包，等服务端展开；打印放了、删了多少物件，新建了哪些锚点，**跳过了哪些锚点**（写明"已存在"还是
   "曾经存在"），**锚点漂移**（关联的物件挪了、锚点没动）；
5. 生成预览链接（`--no-preview` 不生成），把草稿记进 `out/drafts.json`；`--publish` 时直接发布（要有发布权限）。

**跳过的锚点**可能是被别人用掉了编号，请人判断；**锚点漂移**要用实体区草稿去挪锚点（`metaverse build` + `metaverse push`）——重建包
不会改已有的锚点。

## 7.3 看预览、发布

人打开预览链接看：

- [ ] "优化"视图：结构不歪、物件齐全、朝向对、没有悬空和穿插；近看材质对；
- [ ] "原始"视图：扫描没变时和上一版完全相同；
- [ ] 画面底边有 CC-BY 模型的署名行，"全部来源"列出每个外部模型；
- [ ] 跳过的锚点、锚点漂移都处理过或确认不用处理。

```bash
metaverse publish <草稿编号>               # 说明默认取清单的 note
metaverse publish <草稿编号> --replay      # 冲突时：在最新版本上重放
```

- **冲突**：重建层整体是一个冲突单位——草稿的基础版本之后有别的提交改过重建层（同一个包清单发布的不算），发布返回 409，键是 `layer:rebuilt`；另有 `scan`
  （中途有人换了扫描）、`anchor:<编号>`（新建的锚点中途被别人建过、改过、删过）。确认后 `--replay` 在最新版本上重放（整体替换会把中途
  别人改的重建层也换掉），或者 `metaverse pull` 后重新打包。实体区草稿和重建草稿只在同一个锚点编号上才会冲突。
- **没有变化**：内容与最新版本完全相同时不写提交，显示"没有变化"——同一个包重推、重发都是幂等的（中途同一个包清单发布的提交不算
  冲突，不用加 `--replay`；中途还有别的包改过重建层时照样 409）。
- **模板引用缺失**（409 `broken_template_ref`）：有物件引用的模板不在同一层；按列出的编号补模板或改引用。
- **资源被清理**（409 `asset_gone`）：草稿放太久，引用的文件被清理了；重新 `bundle push`（内容相同，哈希相同）。

发布后的提交：`actor.kind = rebuild`；扫描没变时不写扫描，回放沿用上一次；拍摄时间没给、扫描又没变时沿用上一次的；网页用模型、物件模型、
贴图登记进公开资源；原始扫描、清单、建模记录只被提交引用，不公开，预览链接也拿不到。

## 7.4 权限

| 要做的事 | 要什么 |
|---|---|
| 推送（上传、建重建草稿、交包、预览） | 空间的"管理"级别（主人本人、主人组织、组织 admin）**并且**令牌带 `metaverse:rebuild:write`；没有就 403 `rebuild_permission_required` |
| 发布 | 同上；给 AI 用的 agent key **默认不给发布**，人看过预览再发布 |
| 读（拉取、查任务） | 访问级别即可 |

- `metaverse:rebuild:write` 由 NyxID 的角色带来：请平台管理员建角色 `metaverse-rebuilder`（只含这一项权限），分给要写重建层的人。
  **在这之前，通过接口谁都写不了重建层**，只有部署种子能写——这是有意的。
- AI 一律用自己的 agent key（`nyxid login --agent-key --profile <名称>`，人审批），操作范围只开 `/spaces/<空间>/rebuild/` 下的上传、建草稿、
  交包、预览、任务查询，不开发布；不要让 AI 用人的登录态（人的全部权限都会给它）。
- 详见[整体设计](../ARCHITECTURE.md) 9.2、9.3 和设计第 3 节。

## 7.5 演示种子

演示空间（`chronoai-lobby`）由接口服务启动时的部署种子导入。线上不跑任何重建：种子配置按哈希固定两份小文件——**清单**和**来源表**
（每个文件从哪里下载）——执行器下载、核对、登记，再走与命令行相同的展开和发布。

```bash
# 1. 在工作区里取线上的变换和网页用模型（只有分享链接、不是组织成员时也能用）
metaverse pull --share <演示链接> --assets
# 2. 扫描按来源表的成员、同样的顺序打包（哈希应等于线上已有的扫描）
metaverse-recon scan-zip ...
# 3. 打种子用的包：去掉内部级锚点和建模记录，report 只留偏差统计
metaverse-recon bundle --seed --webmodel <线上那份> --authored <物件集>
metaverse bundle check --seed     # 发现内部级锚点或建模记录会警告
```

4. 大文件改名成 `<sha256>.<扩展名>`，上传到本仓库的发布页 `demo-assets`（`gh release upload demo-assets ...`，同名已存在就跳过）；扫描 zip
   不重新托管，来源表的 `zip` 指向 Scaniverse 原地址的成员；
5. 写来源表 `sources.json`（键是清单里的 sha256，值是 `url` 或 `zip` 成员表）；
6. 清单和来源表提交进 `infra/chrono-cd/demo/<空间>-r<版本>/`；
7. 种子配置（`METAVERSE_DEMO_SEED`）的 `revision` 加一，`bundle.manifest`、`bundle.sources` 写按提交哈希固定的 raw 地址、sha256 和大小；
   跑 `node infra/chrono-cd/check-app.mjs`；
8. 本机用新库全流程跑一遍（`infra/dev/up.sh --demo-seed=<这份种子>`），再部署。

注意：

- **种子包里的一切都会公开**（公开仓库、公开发布页）：全部锚点、`report`、建模记录。所以必须用 `--seed`；非公开的内容用命令行直接推送，
  不进种子。
- 大文件放发布页是推荐方案，**待用户确认**（设计第 14 节）。
- 同一版本只导入一次；下载类失败（发布页刚上传时 404、限流）在下次启动时自动重新排队，修好后重启就能接着导入，不用改版本号。
- 内容或配置有错（哈希不符、清单不合规）不会重试：改好后版本再加一。
- 种子发布遇到冲突自动在最新版本上重放（种子没有人工确认这一步，内容由部署配置钉死）。

## 7.6 验证

| 看什么 | 期望 |
|---|---|
| 时间线 | 新的一版追加在最后；能回到之前任何一版 |
| "原始"视图 | 扫描没变时与上一版完全相同（网页用模型哈希不变） |
| "优化"视图 | 是新的一版；外部模型、手写形状、贴图都在；近看材质对 |
| 提交的拍摄时间 | 是扫描的拍摄日（扫描没变时沿用上一次） |
| 署名 | 有 CC-BY 模型时画面底边常驻署名行；"全部来源"完整 |
| 信息面板 | 点选物件能看到它的偏差和来源 |
| 加载 | 优化视图几秒内画出；接口数据量在预期内（第 3 版约 2.85 MB） |
| 种子 | 接口服务日志里种子任务 `done`；分享链接不变 |

## 7.7 回滚和修正

- **时间线只追加**：发布错了，再发布一个修正的包。
- **回到某一版的重建层和扫描**：`metaverse pull --share <链接> --seq <那一版>`，`metaverse-recon bundle --from-snapshot <工作区>` 打成整体
  替换的包（编号换成 `rb.` 开头），再推送发布。
- **包不能删锚点**：重建包新建的锚点要删，用实体区草稿另外删。
- 演示空间：把种子配置退回上一个版本只是不再导入新版本，已经发布的提交仍然是最新的一版；要让内容回到上一版，按上面
  `--from-snapshot` 的做法发布一个修正的包（种子版本再加一）。
