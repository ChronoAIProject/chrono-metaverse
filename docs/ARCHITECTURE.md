## 1. 目标与范围

### 1.1 要做什么

1. **实体餐厅的数字孪生**（同一流程也用于前厅、花店等其他实体空间）：导入 Scaniverse 扫描（glb、Draco 等网格模型），由 AI 按扫描的真实轮廓重建出干净的 3D 模型（优化模型），贴图从原扫描转移过来。
2. **开放虚拟位置**：在孪生旁边扩展出现实中不存在的虚拟区，划成地块，通过 NyxID agent key 授权给合作方或 AI 建造。
3. **一条时间线**：空间的每次变化、现实中发生的每件事都按时间记录，可以回放到任意时刻。
4. **三种视图**：原始模型 / 优化模型 / 优化模型 + 虚拟扩展。
5. **多空间组合**：多个空间（餐厅、花店……）拼在一起展示，跨空间事件（送花）同步回放。
6. **权限**：完全使用 NyxID 的鉴权和权限体系。每个 agent 用一把 NyxID agent key，由人在 NyxID 里限定它能改哪个空间、哪个地块、写哪类数据（第 9 节）。
7. **NyxID 服务**：用 NyxID 鉴权，注册成 NyxID 服务，AI（Claude Code / Codex）经 NyxID 调用。部署在 chrono-cd，数据存 MongoDB。

### 1.2 明确不做

- 不是多人游戏：没有化身，也没有多人实时同步。
- 网站只读：所有人只能看，不提供网页编辑器，也不提供网页上传。
- 不做分支：只有一条时间线（定义见第 2 节）。
- 不自己实现 MCP：只提供 OpenAPI 文档，由 NyxID 生成 AI 工具。
- 云端不做截图渲染：AI 在本地出图（第 10 节）。

### 1.3 核心原则

- **读写分离**：读走网站和公开读接口；写只能走写接口，必须经过 NyxID 鉴权，权限由 NyxID 决定。
- **只追加**：已发布的数据只追加，不修改、不删除。录错了就追加更正。唯一的例外是法律要求删除个人信息（13.4）。
- **一切修改入时间线**：每次修改都记录操作人、作用范围和时间。
- **权限边界**：身份、权限、组织成员关系和角色、agent 能做什么，都由 NyxID 给出；本服务只存"资源归哪个 NyxID 主体"这一个事实（9.2）。
- **重计算在本地或任务里**：接口服务不做长时间计算，单个请求控制在 100 秒内。

### 1.4 分阶段开放

| | 第一步：组织内部 | 第二步：对外开放（稳定后） |
|---|---|---|
| NyxID 注册 | 先在 ChronoAI 组织下自助注册自定义服务跑通；要用 agent key 的参数限制时，由平台管理员注册成目录服务（9.3） | 目录服务，所有用户自动可用 |
| 谁能写 | ChronoAI 组织成员及其 agent key（9.2、9.3） | 任何 NyxID 用户及其 agent key（自助建空间） |
| 谁能看 | 知道分享链接的人 | 同左；另外可以设为公开，进入空间目录 |
| 配额、举报、计费 | 只做基本上限 | 完整配额、举报下架、可接 NyxID 计费 |
| 命令行与技能文件 | 组织内部使用 | 发布到 npm，技能说明公开 |

第一步就按对外开放的结构来写：空间归属、配额字段都预留好，只把"谁能用"限定为组织成员。

## 2. 术语

| 术语 | 含义 |
|---|---|
| **网格** | 全系统统一的定位网格，单位 `GRID_UNIT` 按真实物体尺度定为 5 厘米（约为一把椅子宽度的 1/9），所有空间共用，上线后不可改。网格只用于定位、区域和地块边界、锚点吸附和占用索引；模型几何用连续坐标，不吸附到网格 |
| **一条时间线** | 全局唯一的时间轴。所有空间提交、组合修订和事件都按服务端时间 `at` 排在上面；各空间、各组合的序号 `seq` 只用于存储分区和并发控制，不是独立的时间线 |
| 空间 | 一个独立的方块世界，有自己的坐标系和方块表 |
| 实体区 / 虚拟区 | 空间里与现实对应、由扫描生成的部分 / 现实中不存在的扩展部分 |
| 地块 | 虚拟区内划出的一块范围，可以单独授权 |
| 图层 | 扫描层（原始模型）、重建层（AI 按扫描轮廓重建的结构和物体）、扩展层（人和 AI 的修改：物件，以及可选的方块） |
| 区块 | 方块风格内容的存储单位，32×32×32 格（用于虚拟区的方块建造和占用索引） |
| 方块表 | 空间内方块编号到方块定义（颜色、贴图、材质）的对应表，编号只增不改 |
| 物件 | 非方块的模型，比如一束花或一盏灯 |
| 锚点 | 现实对象在孪生里的位置，比如桌号、座位、区域、门、摄像头 |
| 提交 / 修订 | 空间的一次变更 / 组合的一次变更 |
| 事件 | 一条现实发生的事，挂在锚点上 |
| 草稿 | 还没发布的修改，用于预览和确认 |
| agent key | NyxID 签发给某个 agent 的凭证（`nyxid_ag_` 开头），只保存在 agent 本机；能做什么由人在 NyxID 里配置的操作范围决定 |
| 操作范围 | NyxID 对 agent key 的限制：允许哪些接口、路径参数和请求体字段取什么值 |
| 分享令牌 | 打开"凭链接查看"的空间时用的随机令牌 |
| 组合宇宙 | 引用多个空间并规定它们的摆放方式 |

## 4. 数据模型

### 4.1 空间

```
spaces {
  _id: "restaurant-xyz"            // 空间编号；不当作秘密
  name, description,
  owner: { kind: person | org, id }   // 主人：NyxID 个人或组织（9.2）
  ownerEvidence?: { issuer, orgId, verifiedBy, verifiedAt, basis, roleAtVerification? }   // 组织空间创建时的核验记录，之后只读
                                   // basis：org_subject | org_admin | operator_seed（部署配置种子，9.2）
  visibility: unlisted | public    // 第一步只用 unlisted（凭分享令牌）
  shareTokens: [ { id, hash, createdAt, revokedAt } ]   // 至少 128 位随机数，只存哈希，可轮换、可吊销
  frame: { fixedAt, referenceScan } // 坐标系：首次导入扫描时固定，之后不变
  head: { seq, at, commitId }      // 时间线最新位置
  regions, plots                   // 当前状态（只作读缓存；历史在提交里，见 5.2）
  storageLimitBytes, storageUsedBytes
  createdAt
}
```

- **坐标**：y 轴向上，单位米；网格坐标 = 米 / `GRID_UNIT`。原点在首次导入扫描时定在实体区地面的一个角，之后固定不变；重扫的对齐方法见 6.2。
- **区域和地块**：形状是若干个轴对齐的盒子 `[x0,y0,z0,x1,y1,z1]`，单位是格；变更通过提交完成。

### 4.2 图层、几何与区块

- **三个图层**：
  - **扫描层**：原始模型资源 + 对齐变换。
  - **重建层**：AI 按扫描轮廓重建的结构元素（地面、墙、玻璃，带转移来的贴图）和物体（参数化定义 + 贴图），只在实体区；以物件记录（4.4）存储，随提交版本化。
  - **扩展层**：人和 AI 的修改，可以是参数化物件，也可以是方块风格的格子（区块）。
- **几何用连续坐标**：顶点、物体的位置和旋转都是连续值（米），不吸附到网格。网格只用于定位参考、区域和地块边界、锚点吸附，以及占用索引（寻路、找空位）。
- **方块是可选风格**：虚拟区可以用方块建造，方块按网格存成区块，编码如下。
- **区块编码**：
  - 每个区块是 32³ 个 16 位方块编号，按固定顺序 `index = x + 32·(z + 32·y)` 排列，小端 uint16，组成规范字节。
  - **区块哈希** = SHA-256(格式版本号 + 规范字节)。压缩只是存储细节，`chunks._id` 就是这个哈希。
- **保留编号**：
  - 0 表示"空"或"不覆盖"；
  - 1 表示"空气覆盖"，只在扩展层有效，用来删除下层的方块；
  - 方块表的编号从 2 开始。
  - 全 0 的区块不进清单。
- **扩展层优先**：扩展层的物件可以替换或隐藏重建层的物件（例如重新布置桌椅），扩展层的方块覆盖同一位置的方块，所以重新重建实体区不会冲掉手工修改。
- **区块变化记录**：提交里 `changedChunks` 的 `hash = null` 表示删除这个区块。重新生成方块时，旧清单里有、新结果里没有的区块必须写 null。

### 4.3 方块表

```
palettes { _id: 内容哈希, spaceId, blocks: [ { id, name, kind: solid|glass|emissive|…,
           color | texture: { top, side, bottom }(资源哈希), tags } ] }
```

- **只追加**：编号一旦分配就永不复用，也不改它指代的方块；只允许在新版本里修正贴图。
- **重扫**：重扫生成的专属方块追加新编号，旧编号保留，扩展层里对旧编号的引用不受影响。
- **通用方块**：系统自带一套通用方块（石、木、玻璃、金属……），每个空间创建时自动带上。
- **谁来分配**：新编号只由服务端在发布时分配；草稿里新增的方块用临时名称引用，发布时换成正式编号。新的方块表版本在提交事务前按最新版本算好、按内容哈希写入，由 `head.seq` 条件保证编号不冲突。
- **哪一版生效**：每次提交和每个关键帧都记录 `paletteHash`；回放时用 T 时刻生效的那一版方块表。

### 4.4 物件和锚点

两者都按"版本记录 + 当前状态"存储：

```
records { _id: 内容哈希, kind: entity | anchor, spaceId, body }
// 物件 body：{ entityId, layer: rebuilt | ext, kind: structure | object,
//             shape?（参数化定义：基本形体、轮廓放样、模板实例）, assetHash?（生成的模型）, textures?,
//             position, rotation, scale（连续值）, regionId, anchorId?, props }
// 锚点 body：{ anchorId, kind: table|seat|zone|door|camera|counter|space,
//             box | position, label, visibility: public|internal }
entities / anchors（当前状态，只作 head 的读缓存）
```

- **历史**：每次提交用 `changedEntities` 和 `changedAnchors` 记录变化，格式是 `{id, hash | null}`，null 表示删除。回放以提交记录为准。
- **事件只引用锚点编号**：重新装修后只需移动锚点，历史事件仍然显示在当时的位置上。
- **空间级锚点**：保留锚点 `_space`，用于营业状态这类针对整个空间的事件。
- **物件模型**：`assetHash` 只能引用经处理服务校验并重新导出的模型（6.1），网站也只加载处理后的版本。
- **自定义属性**：物件的 `props` 是不透明的键值。网站只在点选物件时，在信息面板里按纯文本列出（保留键 `label` 作为悬浮标签），不做其他解释。

### 4.5 组合宇宙

```
universes { _id, name, owner: { kind: person | org, id }, visibility: unlisted | public, shareTokens,
            head: { seq, at },
            members: [ { spaceId, offset: [x,y,z], rotation: 0|90|180|270 } ],
            links:   [ { from: {spaceId, anchorId}, to: {spaceId, anchorId}, kind: door|portal|street } ] }
universeRevisions { universeId, seq, at, actor, message, state: { members, links } }
```

- **摆放**：`offset` 以格为单位；`rotation` 绕 y 轴、以成员空间原点为轴心，先旋转再平移。所有空间共用同一个格子尺寸，所以网格天然对齐。
- **修订**：每次修订都存完整的新状态（体积很小），查 T 时刻的组合只需取 `at ≤ T` 的最后一条修订。
- **写入规则**：与空间提交相同（5.2、5.7）。
  - 修订的 `at` 由服务端赋值 = max(当前时间, head.at)，随 seq 单调不减，调用方不能指定。
  - 在一个事务里插入修订（`(universeId, seq)` 唯一），并按 `head.seq == 旧值` 条件推进 `universes.head`。
  - 调用方用 `baseSeq` 或 `If-Match` 说明自己基于哪个修订，组合已变就返回 409。
- **连接**：`kind` 只决定外观。网站在两端锚点画连接标识，点击后镜头飞到另一端；画跨空间路线时，连接两端作为途经点。不涉及化身或移动。
- **权限与可见性**：见第 12 节。

## 5. 时间线

### 5.1 一条时间线，两类数据

| | 空间变化 | 现实事件 |
|---|---|---|
| 例子 | 导入扫描、生成方块、装修、建虚拟地块、移动锚点 | 入座、点单、出餐、花送达、营业状态 |
| 频率 | 低 | 高 |
| 存储 | 提交 + 区块快照 | 事件流 |
| 显示 | 改变 3D 场景本身 | 按事件类型的显示规则做可视化（5.4） |
| 时间 | 服务端发布时间 `at`，不能补录到过去；现实发生时间只记在 `observedAt` | 现实发生时间 `at`（可以晚到）+ 服务端记录时间 `recordedAt` |

### 5.2 提交

```
commits {
  _id, spaceId, seq,                    // (spaceId, seq) 唯一
  at,                                   // 服务端赋值 = max(当前时间, head.at)，随 seq 单调不减；调用方不能指定
  observedAt?,                          // 现实中发生的时间（如扫描拍摄日），只用于显示
  actor: { sub, nyxServiceId, scope: physical | plot:<编号> | source:<名称>, kind },   // 发布者；NyxID 补上 agent key 编号后增加 agentKeyId（9.6）
  author?: { sub },                     // 草稿创建者（与发布者不同时记录）
  message,
  ops | opsRef,                         // 内联上限约 1MB，超出就存成资源，这里只放哈希
  changedChunks:   [ { layer, cx, cy, cz, hash|null } ],
  changedEntities: [ { id, hash|null } ],
  changedAnchors:  [ { id, hash|null } ],
  regionsHash?, paletteHash?, scan?: { assetHash, webModelHashes, transform },
  keyframe?: 状态清单的哈希,             // 每 50 次提交存一份完整状态（区块、物件、锚点、区域、方块表、扫描）
  jobId?,                               // 由任务产生的提交；(jobId) 部分唯一索引，防止重复写回
  draftId?, scriptRef?                  // 草稿发布时附带的脚本（资源哈希，只为追溯）
}
```

**跳到时刻 T**：
1. 先用 `(spaceId, at)` 索引找出 S = `at ≤ T` 的最大 seq；
2. 再取 `seq ≤ S` 的最近一个关键帧 K（按 seq 找，不按时间找）；
3. 最后叠加 (K, S] 范围内各次提交的变化。

整个过程不需要重放操作。

**重扫**：追加一次"导入扫描 + 重新 AI 重建"的提交，时间线上就能看到店铺的真实变化。对齐方法见 6.2。

### 5.3 现实事件

```
events {
  _id, spaceId, at, recordedAt,         // recordedAt 由服务端赋值；at 晚于 recordedAt + 5 分钟的拒收
  source,                               // 来自路径 /sources/{source}；谁能写哪个数据源由 NyxID 操作范围决定
  sourceEventId,                        // (spaceId, source, sourceEventId) 唯一，用于去重和安全重试
  type, typeVersion, anchorId,
  data,                                 // 按事件类型的 JSON Schema 校验，不超过 4KB
  visibility: public | internal,        // 不填时取事件类型的默认值
  correlationId?,                       // 跨空间关联，格式 "<发起空间编号>:<编号>"
  corrects?, retracted?, redacted?
}
```

- **更正**：
  - 分两种：**替换**（完整的新记录，`at` 与原事件相同）和**撤回**（`retracted: true`，不带内容）。
  - `corrects` 一律指向最初那条事件；同一事件有多条更正时，以 `recordedAt` 最新的一条为准。
  - 原事件的时间录错了，就先撤回，再写一条新事件。
  - 更正走同一数据源的路径（`/sources/{source}/corrections`），所以只有能写这个数据源的 agent key 或空间主人能更正。
- **公开过滤顺序**：先应用更正，再按可见级别过滤。被替换掉的原版本永远不出现在公开接口里，所以把公开事件更正成内部级，它就会从公开接口消失。
- **抹除**：空间主人可以经管理接口抹除一条事件的内容（8.4），之后公开接口和 `/api/v1` 的读接口都不再返回它的 `data`。

### 5.4 事件类型与显示规则

网站是固定的只读查看器，"自定义交互"全部用声明式的数据来表达：

```
eventTypes { spaceId, type, version,           // 只追加的版本记录；回放用 T 时生效的版本
  schema,                                      // JSON Schema
  publicFields: [ 路径 ],                       // 公开接口只返回这些字段
  defaultVisibility,
  state?: { key, value, clears? },             // 有 state 表示"从此刻起该锚点处于某状态"，直到同一 key 的下一条
  maxAgeSec?,                                  // 状态多久没更新就自动失效（防止漏记结束事件时一直亮着）
  display: { kind: highlight | icon | label | path | spawnEntity | heat,
             icon?, color?, durationSec?, labelTemplate?(只能引用公开字段),
             entityAsset?, pathRole?: origin | destination, heat?: { windowSec, weight? } } }
```

- 网站只实现上面这几种显示方式。新增一种交互 = 登记新的事件类型，组合已有的显示方式，**不用改网站代码**。
- 例子：
  - `table.occupancy`：`state.key = "occupancy"`，显示为桌子高亮。
  - `order.served`：显示一个图标，3 秒后消失。
  - `delivery.sent` 和 `delivery.arrived`：显示为路线，分别是 `pathRole = origin` 和 `destination`。

### 5.5 回放与"现在"模式

- **瞬时事件**：显示 T 附近一个时间窗内的事件。
- **状态事件**：对每个 (锚点, 状态 key)，取 `at ≤ T` 的最后一条有效事件（更正已应用），不受时间窗限制，所以 T 时刻每张桌子的状态都是对的。读接口 `GET .../state?at=` 直接返回这个结果；服务端定期保存状态快照，避免每次从头扫描。
- **"现在"模式**：
  - 页面打开时先调用 `state?at=<当前时间>` 取得各锚点的当前状态，再增量更新。
  - 网站每隔几秒（至少 5 秒）查询一次 `/head`，带 ETag，没有变化时返回 304。
  - 有变化时按 `since=<recordedAt 游标>` 增量拉取事件，晚到的事件和更正都能拉到。
  - 客户端每次把游标往回退几秒，再按事件编号去重。
  - 之前公开过、后来被撤回或改成内部级的事件，增量结果里会带一条"撤下"标记。
- **组合回放**：先取组合在 T 时刻的修订（成员、摆放、连接），再让每个成员空间按 5.2 的方法各自求出 T 时刻的版本。

### 5.6 草稿

```
drafts { _id, spaceId, scope: physical | plot:<编号>, baseSeq, rev, createdBy: { sub },
         ops, touched: { chunks, entities, anchors, regions, plots },
         resultChunks: [ { layer, cx, cy, cz, hash } ], assets, expiresAt }      // 30 天过期；assets 是草稿引用的资源哈希
draftChunks（草稿生成的区块，随草稿过期删除，不写进 chunks）
```

- **自查**：本地建造的 AI 在本地出图自查（10.1）；只用 AI 工具的小改动可以先不出图，人看预览链接确认。
- **预览**：
  - 令牌是 256 位随机数，库里只存哈希，绑定 `{空间, 草稿, rev}`。
  - 默认有效 24 小时，最长 7 天；草稿发布或丢弃时，令牌立即失效。
  - 链接形如 `/preview#t=<令牌>`，令牌放在 `#` 后面，不会进入服务器和网络层的日志。
  - 预览和公开接口一样，只显示公开锚点和公开事件；响应不缓存。
  - 预览用到的全部区块和资源都走预览专用接口（8.2），凭预览令牌读取。服务端只返回属于这次预览的内容：草稿生成的区块、草稿引用的资源（`assets`），以及草稿基础版本及更早（seq ≤ `baseSeq`）的提交引用过、已发布的区块和本空间已登记（`assetRefs`）的资源；其他哈希一律 404。草稿区块和草稿新上传的资源在发布前只能这样读到。
- **草稿范围**：草稿属于创建时的路径范围（实体区或某个地块）。追加操作、生成预览、发布都必须走同一范围的路径，谁能调这些路径由 NyxID 操作范围决定。
- **发布**：
  - 如果时间线已经前进，就拿 (baseSeq, head] 之间各提交的变化和草稿的 `touched` 求交集：没有交集就直接叠加到最新版本上发布；有交集才返回 409，并列出冲突的键。
  - 调用方可以请服务端在最新版本上重放草稿的操作。
  - 只是重新重建了实体区、草稿只改扩展层的情况，不算冲突。
  - 发布时，按最新的区域和地块重新校验全部操作是否仍在草稿范围内。提交的 `actor` 记发布者，`author` 记创建者。
  - 提交的 `at` 取发布那一刻的时间。

### 5.7 并发与事务

- **事务外**：新区块、状态清单、大块操作按内容哈希幂等写入（重复键直接忽略）。这些写入失败时只会留下无人引用的对象，不影响正确性。
- **事务内**：只做这几件事——插入提交（seq 唯一）、按 `head.seq == 旧值` 条件推进空间指针（区域和地块的当前状态一起更新）、更新物件和锚点的当前状态、登记资源引用 `assetRefs`；由任务产生的提交，再加上 6.4 的任务状态条件更新。事务很小，不会碰到 MongoDB 的事务大小和时长上限。
- **事务后**：给本次新引用的区块打上 `publishedAt`（幂等，失败可以补做）。草稿发布时，先把用到的 `draftChunks` 复制进 `chunks`。
- **直接写入**：调用方用 `baseSeq` 或 `If-Match` 说明自己基于哪个版本，版本已变就返回 409。草稿发布按 5.6 的规则处理。

## 6. 扫描处理

扫描由云端处理服务处理并写入时间线，重建层只由任务写入。本地可以用同一个处理镜像试跑、调参和预览（第 10 节），确认后用同样的参数发起云端任务。

### 6.1 上传

- **创建上传**：
  - 声明总大小、整体 SHA-256、分片大小和用途（scan / model / texture / ops / script / authored）。
  - 用途写在路径里（`.../uploads/{purpose}`），能上传哪类文件由 NyxID 操作范围决定；地块路径下不能上传扫描。
  - 如果这个哈希已经存在，直接复用，不再接收数据。
- **大小上限**（可配置）：扫描 ≤ 1GB，物件模型 ≤ 50MB，单张贴图 ≤ 8192×8192。
- **格式**：模型和贴图只接受 glb、drc、obj、png、jpeg、webp；ops 用途只接受 NDJSON（可用 gzip 压缩）；script 用途只接受纯文本；authored 用途（AI 物件集，见 6.3）只接受 JSON 对象，≤ 4MB，只经实体区路径。
- **分片**：
  - 分片大小在创建时固定，是 256KiB 的整数倍，最大 32MiB；除最后一片外，各片大小相同。
  - 服务端把每片切成固定 256KiB 的 GridFS 数据块写入（`files_id` = 上传编号，序号按片号推算），并记录这一片的 SHA-256。这样做是因为 GridFS 要求同一文件的数据块大小一致，而单个文档不能超过 16MB。
  - 同一片重传时，先删掉它原有的数据块，所以重传是幂等的。
  - 片数不能超过 ceil(总大小 / 分片大小)；累计数据超过声明的总大小就拒绝。
  - 超过配额或空间存储上限时返回 413 或 429。
- **完成上传**：
  - 返回 202 和任务编号。处理服务流式计算整体哈希，核对通过后才登记成资源（文件名 = 内容哈希，唯一索引）。
  - 登记时如果遇到文件名唯一键冲突（同一内容被并发上传），就删掉本次的数据块，复用已有资源。
  - 整体哈希核对失败时，同样删掉本次的数据块，并把上传标记为失败。
- **物件模型**：物件模型和贴图上传后，先由处理服务校验，并重新导出成受限的 glb（限制三角形数和贴图尺寸）。"放物件"只能引用处理后的版本。
- **清理**：
  - 处理服务定期清理超过 24 小时还没完成的上传（先删除 `files_id` = 上传编号的 GridFS 数据块，再删除上传会话），以及完成后 7 天内没有被任何提交或草稿引用的资源。
  - 清理先查引用、再按"`touchedAt` 仍早于 7 天前"的条件删除，两步之间没有锁。所以接口服务和处理服务新引用一个已有资源之前（草稿追加、发布、建任务、复用上传、登记资源），都先按文件名刷新 `touchedAt` 并要求匹配到；匹配不到说明刚被清理，按资源不存在处理，让调用方重新上传（内容相同，哈希也相同）。发布时在提交事务里再确认一次，缺了就整个提交作废（409 `asset_gone`）。
  - 这些数据还没进时间线，删除它们不违反只追加原则。
  - 平台没有定时任务，所以清理放在处理服务的循环里做。

### 6.2 对齐

- **首次扫描**：
  1. 找到地面并摆正；
  2. 按墙面法线的主方向绕竖直轴旋转，让墙和网格轴对齐（实测前厅旋转约 −61°，见 16 节）；
  3. 原点定在实体区地面的一个角，坐标系从此固定。
- **重扫**：
  1. 先按同样的方法粗对齐（主墙的 4 个 90° 朝向都试一遍）；
  2. 再和参考扫描做点云配准，只求绕竖直轴的旋转和平移，只用地面、墙等稳定结构，并剔除离群点，避免真实的装修变化把结果带偏；
  3. 配准误差随参数一起写进时间线；超过阈值就不自动提交，转人工经接口微调。

### 6.3 AI 重建（优化模型）

验证见 `spikes/parametric/`。流程：

1. **结构**：用平面拟合找出地面、墙、玻璃（包括非轴向的墙），按分段处理扫描漂移，墙角吸附；再把原贴图投影到各个平面。
2. **物体分割**：去掉结构上的点，在空间里聚类。AI 看渲染图确定每一簇是什么——图片只用于识别。
3. **按轮廓重建**：
   - 从扫描网格切出各高度的截面轮廓，简化并规整（平行、对称），再放样成曲面；
   - 规整的部分可以用基本形体；
   - 几何用连续坐标表示，不吸附到网格。
4. **同款物体合并**：同款物体（例如会议椅）对齐后合并点云，互相补齐遮挡，重建成一个模板，再在各处按实例摆放。
5. **贴图转移**：给新几何展开 UV，每个纹素取原扫描最近表面的颜色，所以材质、缝线、木纹都和原来一致。
6. **自查**：渲染对比，计算扫描表面到模型的距离；由评审 AI 找差异，再修一轮。
7. **写入时间线**：结果写成一次提交，内容是结构元素和物体记录（参数定义 + 贴图资源），每个物体带建议的锚点编号。
8. **网页用模型**：为原始扫描生成压缩版和多级细节版本，供"原始"视图使用。
9. **方块化（可选）**：需要方块风格时，仍可以按网格体素化（`spikes/voxelize/`）。

识别和拆分需要 AI 参与：可以由处理服务调用 AI 完成，也可以由本地的 AI 完成后上传结果（第 10 节）。

**AI 物件集写回**：本地的 AI 逐件完成的物件（先去模型库找看起来差不多的现成模型，找不到再手写参数形状）写成
`{version: 1, templates, entities, notes?, structure: keep | replace}`，经 `scan_import` / `rebuild` 任务的
`authored`（内联，接口服务登记成资源）或 `authoredAsset`（authored 用途上传）写进时间线：

- 接口服务只做浅层校验（结构、数量 ≤ 2000 物件 / ≤ 200 模板、≤ 4MB、地址必须 https、烘焙指令的位置），
  深层校验（形状、记录、模板引用、署名许可）在处理服务，不合格时任务失败；
- 结构按 `structure` 沿用算法结果或用物件集里的结构；带烘焙指令 `bake` 的部件从扫描烘焙贴图；
- 外部模型（Poly Haven、Objaverse 里许可为 CC0、CC-BY 的）只从配置的主机经 https 下载（重定向逐跳检查），
  核对大小和 sha256，把旋转、缩放、调色烘进网格，按物件模型的限制重新导出 glb，写成 `assetHash`；
  `props.source` 记作者、来源页、许可，网站显示"模型来源"；
- 逐件计算扫描到物件的偏差写进 `fit`；`notes` 存成脚本资源，提交的 `scriptRef` 指向它；
- 重建层全部换成这次的结果，锚点规则不变。部署种子可以带物件集（`infra/chrono-cd/README.md`）。

格式和规则见 `worker/README.md`"AI 物件集"。

### 6.4 任务

```
jobs { _id, spaceId, kind, params, status: queued|running|done|failed,
       leaseOwner, leaseUntil, attempt, maxAttempts(默认 3), lastError, resultCommitId, createdAt }
```

- **领取**：用一次原子更新领取排队中的任务，或租约已过期且重试次数未用完的任务，同时写入租约（3 分钟）并把重试次数加 1。
- **续约**：每 30–60 秒续一次约，续约条件要带上租约持有者和重试次数。续约失败说明租约已经丢了，处理进程必须放弃，不能再写回结果。
- **写回**：
  - 结果提交带 `jobId`（`commits.jobId` 部分唯一索引）。
  - 在同一个提交事务里按条件更新任务：条件是 `{_id, attempt, leaseOwner, status: running}`，更新为 `status = done` 并写入 `resultCommitId`。匹配数为 0 或 jobId 唯一键冲突时，中止事务并丢弃结果。
  - 领取任务时如果发现已经有带这个 jobId 的提交，直接把任务标记为完成，不再重做。
- **解析前检查**：
  - 解析模型前，先读文件头，检查三角形数、贴图解码后的像素总数，以及"包围盒与实体区的交集 / GRID_UNIT³"是否超过上限；超过就直接把任务标记为失败。
  - 解析和体素化放在子进程里，并设内存上限和超时。
- **失败**：重试次数用完后标记为失败。
- **并发**：每个空间同时运行的任务数有上限；一个空间的失败任务不能阻塞其他空间的队列。
- **索引**：`(status, createdAt)`（按先后领取）、`(status, leaseUntil)`（回收过期租约）、`(spaceId, status)`。
- **可见性**：任务进度和失败原因可以经接口查询。

## 7. 网站（只读查看器）

### 7.1 三种视图

视图 = "取哪些图层，按区域过滤"：

| 视图 | 模型（时刻 T） | 物件 | 公开锚点和事件 | 虚拟区标识 |
|---|---|---|---|---|
| 原始 | T 时最新的扫描（网页用模型，按对齐变换）；T 之前没有扫描就提示 | 不显示 | 显示 | 无 |
| 优化 | 重建层 ⊕ 扩展层，只取实体区 | 实体区物件 | 显示 | 无 |
| 优化 + 扩展 | 重建层 ⊕ 全部扩展层（含虚拟区的方块） | 全部物件 | 显示 | 有（边界光效、"虚拟"标签） |

- 视图只改变 3D 场景显示的内容；时间轴和"现在"模式在三种视图下用法一样。
- **剖切**是所有视图共用的相机选项：把某个高度以上的内容（包括扫描模型）都切掉，用来看室内。扫描通常带天花板，这个选项第一版就要做。
- "混合"（扫描范围内显示原始模型，范围外显示方块）和"叠加对比"放到增强阶段。

### 7.2 其他

- **时间轴**：
  - 标出各次提交，显示事件密度（用聚合接口取数）。
  - 支持播放、暂停、调速、跳转，有"现在"按钮。
- **事件可视化**：只实现 5.4 列出的显示方式。事件文本、锚点标签、提交说明一律当纯文本显示。
- **打开方式**：
  - 空间链接形如 `/s/<空间编号>#share=<分享令牌>`；组合链接形如 `/u/<组合编号>#share=<分享令牌>`。
  - 页面脚本把令牌放在请求头 `Authorization: Share <令牌>` 里调用公开读接口。
  - 页面设置 `Referrer-Policy: no-referrer`。
- **加载**：区块和资源按内容哈希命名，可以永久缓存；网格在浏览器的后台线程里生成。

### 8.2 公开读接口

| 接口 | 说明 | 缓存 |
|---|---|---|
| `GET /api/public/spaces/{id}` | 名称、区域、公开锚点 | 短 |
| `GET /api/public/spaces/{id}/head` | 最新 seq、最新事件记录时间 `recordedAt`（含晚到事件、更正和撤回，只统计公开接口可见的变化；带 ETag） | 支持 304；进程内缓存 1–2 秒 |
| `GET /api/public/spaces/{id}/snapshot?seq=` | 该版本的区块清单、方块表、物件、公开锚点、区域和地块、网页用模型 | 长（可在进程内失效） |
| `GET /api/public/spaces/{id}/snapshot?at=` | 换算成 seq 后跳转到上一个地址 | 不缓存 |
| `GET /api/public/spaces/{id}/timeline?from=&to=&after=` | 提交列表（每页 ≤ 500） | 短 |
| `GET /api/public/spaces/{id}/events?from=&to=&since=&types=&after=` | 公开事件（每次 ≤ 24 小时，每页 ≤ 5000） | 短 |
| `GET /api/public/spaces/{id}/events/density?from=&to=&bucket=` | 事件数量聚合（最长 90 天） | 短 |
| `GET /api/public/spaces/{id}/state?at=` | T 时刻各公开锚点的状态 | 短 |
| `GET /api/public/chunks/{hash}.bin` | 区块，只返回已发布（有 `publishedAt`）的区块 | 永久 |
| `GET /api/public/assets/{hash}.bin` | 资源，只返回登记在 `assetRefs` 里的资源，支持分段下载 | 永久 |
| `GET /api/public/universes/{id}?at=` | T 时刻生效的组合修订（成员、摆放、连接）和各成员在 T 时刻的 seq；查看器再按这些 seq 调用 `snapshot?seq=` | 不缓存 |
| `GET /api/public/universes/{id}/revisions/{seq}` | 某一次组合修订的内容 | 长 |
| `GET /api/public/previews` | 草稿预览（令牌放在请求头里） | 不缓存 |
| `GET /api/public/previews/chunks/{hash}`、`.../assets/{hash}` | 预览用到的区块和资源：草稿生成的区块、草稿引用的资源，以及草稿基础版本（seq ≤ baseSeq）的提交引用过、已发布的区块和本空间已登记的资源；不属于这些的一律 404；资源支持分段下载 | 不缓存 |

路径带 `.bin` 扩展名，是为了让平台前面的 Cloudflare 按默认规则缓存这些内容不变的文件：成功响应带 `Cache-Control: public, max-age=31536000, immutable`，不带 Set-Cookie 和 Vary。

**数据投影规则**：
- **提交列表**：只返回 `{seq, at, observedAt, message, actor.kind, changedChunks, changedEntities, changedAnchors}`。其中 `changedAnchors` 按公开投影改写：内部锚点不出现，锚点由公开改为内部时记为删除。不返回用户编号、操作内容和脚本。
- **快照**：只返回在该版本和当前都是公开级的锚点；锚点改成内部级时，清掉进程内对应的快照缓存。扫描只给网页用模型的哈希。
- **区块**：只返回带 `publishedAt` 的区块。在事务外写入、但没有发布成功的区块一律返回 404。
- **资源**：`assetRefs` 只登记网页需要的资源（网页用模型、方块表贴图、处理后的物件模型）。原始扫描、大块操作文件和脚本不登记，只能由有权限的调用者经 `/api/v1` 下载。没有登记的资源一律返回 404。
- **凭链接查看**：
  - 没带令牌或令牌无效时返回 404，拒绝响应一律不缓存。
  - 成功响应一律带 `Cache-Control: private`；只有公开空间的内容才能用 `public`。进程内缓存必须在校验令牌之后才能命中。
  - 组合的分享令牌可以用来读取各成员空间的公开数据：服务端校验该空间在 T 时刻是这个组合的成员。空间主人把空间加入组合（12 节），就等于同意被凭组合链接查看。
- **收不回**：区块和资源一旦发出就收不回。轮换令牌或把公开改成凭链接查看，都撤不回别人已经拿到的哈希和浏览器缓存。把凭链接查看改成公开时，全部历史会随之公开，管理接口要先提示再执行。
- **资源响应头**：资源的 Content-Type 由服务端按用途固定，并加 `nosniff`。

**限流**：
- 所有公开接口按来源地址限流，并对每个空间设全局并发上限。
- `/head` 在进程内缓存 1–2 秒，同一空间每秒最多读一次数据库；进程内缓存同时覆盖快照、区块和资源（有大小上限）。
- 第 0 阶段向平台确认哪个请求头里是可信的客户端地址，以及网关是否只接受来自 Cloudflare 的流量；确认之前来源地址可能被伪造，限流只能当兜底。

### 8.3 写接口与给 AI 的读接口（`/api/v1`）

每个接口都要写 `operationId` 和用途说明，它们会变成 AI 工具名和工具说明：
- **命名**：`operationId` 用小写加下划线（例如 `get_space`）。NyxID 会把它转成小写，非字母数字字符换成 `_`，最终工具名是 `chrono-metaverse__get_space`。
- **路径写法**：OpenAPI 文档里的 `paths` 写完整路径（带 `/api` 前缀）。NyxID 用注册时的地址拼 `paths`，不看文档里的 `servers`。
- **权限信息放在路径里**：空间、地块、数据源这些决定"能不能做"的信息，一律作为路径参数，不放在请求体或查询参数里。这样 NyxID 的操作范围（9.3）可以直接按路径参数限制 agent key。
- **说明**：描述里写清楚用途和上限。

| 分组 | 接口（路径示例） |
|---|---|
| 查看 | `GET /api/v1/spaces/{space_id}`：空间信息，含最新 seq（也作为 ETag）、区域、地块、锚点（含内部级）<br>`GET .../regions/{region_id}/content`：区域内容（分层文字）<br>`GET .../timeline`、`GET .../events`（含内部级）、`GET .../jobs/{job_id}` |
| 实体区修改 | `POST /api/v1/spaces/{space_id}/drafts`：建草稿<br>→ `POST .../drafts/{draft_id}/ops`：批量操作<br>→ `POST .../drafts/{draft_id}/ops-from-upload`：大批量，异步<br>→ `POST .../drafts/{draft_id}/preview`<br>→ `POST .../drafts/{draft_id}/publish` |
| 地块修改 | 同上，路径换成 `/api/v1/spaces/{space_id}/plots/{plot_id}/drafts...`；服务端保证每个操作都落在该地块内 |
| 扫描与上传 | `POST /api/v1/spaces/{space_id}/uploads/{purpose}` → `PUT .../uploads/{purpose}/{upload_id}/parts/{n}` → `POST .../complete`<br>`POST .../scans`（导入）、`POST .../scans/{scan_id}/voxelize`、`POST .../scans/{scan_id}/alignment`、`POST .../scans/{scan_id}/rebuild`（导入、对齐、重建都可以带 AI 物件集，6.3） |
| 事件 | `POST /api/v1/spaces/{space_id}/sources/{source}/events`：批量写，每批 ≤ 1000 条<br>`POST .../sources/{source}/corrections`：更正和撤回 |
| 组合 | `POST /api/v1/universes`<br>`PATCH /api/v1/universes/{universe_id}`：摆放、连接、可见性、分享令牌<br>`POST /api/v1/universes/{universe_id}/members/{space_id}`：加入；`DELETE` 同一路径：退出 |

批量操作只用高层操作（填充、空心盒、替换、复制区域、新增方块、放物件、新建/移动/修改锚点），每次 ≤ 200 条，请求体 ≤ 1MB；超出返回 413，并提示改走上传。

### 8.4 管理接口（`/api/v1/admin`）

包括：创建空间、修改名称和可见性、轮换分享令牌、定义区域和地块、登记事件类型、抹除事件。这组接口不写进注册给 NyxID 的 OpenAPI，所以不会成为 AI 工具，由命令行调用。

- **创建空间**：个人空间由本人创建；组织空间要求调用者是该组织的 admin，创建时现场核验并写入 `ownerEvidence`（9.2）。第一步默认建在 ChronoAI 组织下。
- **不写进 OpenAPI 不等于安全**：这只是为了减少 AI 误用，不是安全边界——NyxID 代理会转发本服务下的任意路径。服务端对每个管理接口都按 9.2 要求"管理"级别。agent key 的操作范围不应包含 `/api/v1/admin` 路径。

### 8.5 经过 NyxID 代理的约束

- **请求头**：自定义请求头会被丢掉（只转发 `If-Match`、`Idempotency-Key`、`Range` 等标准头）。空间编号、基准版本等放在路径、查询参数或请求体里。
- **请求体大小**：单次请求最大 100MB。走 AI 工具时，二进制要由 AI 把 base64 逐字写进工具参数，实际只适合很小的数据，所以大文件一律用命令行分片上传。
- **工具返回**：AI 工具的返回会被转成文本；PNG、JPEG、GIF、WebP 图片不超过 5MB 时，可以直接作为图片返回。
- **超时**：网络层约 100 秒无响应就断开，长时间操作一律做成任务。
- **直连的请求体上限**：
  - 直接访问本服务的请求不经过 NyxID，所以不受它的 100MB 上限约束。
  - 每个路由单独设请求体上限（JSON ≤ 8MB，分片 ≤ 32MiB + 1KiB）：axum 默认对所有提取器限 2MB，按路由用 `DefaultBodyLimit::max(..)`（或 tower-http 的 `RequestBodyLimitLayer`）放到该路由的上限，不设全局的更大上限；超出返回 413。
  - 先校验身份令牌，再读请求体。

## 9. 鉴权与权限（完全使用 NyxID）

本服务不自建任何钥匙或权限体系，也不签发、不保管任何凭证：

- **谁在调用**：看 NyxID 的身份令牌。
- **agent 能做什么**：看 NyxID 的 agent key 及其操作范围。操作范围由人在 NyxID 里配置，NyxID 在转发之前就拦下越权请求。
- **服务端**：只做校验。

### 9.1 身份令牌校验

接口服务部署在 chrono-cd 上，公网可以直接访问，前面没有 NyxID 把关。所以 `/api/v1/*` 必须自己校验 `X-NyxID-Identity-Token`：

- **签名**（按 CMA `auth/nyxid_proxy/jwt.rs` 的做法）：
  - 用 NyxID 的公钥列表（JWKS）校验，只接受 RS256 并按 kid 选公钥；公钥列表缓存 5 分钟，遇到未知 kid 时最多每 5 秒刷新一次；
  - 签发方以 NyxID 的 `/.well-known/openid-configuration` 为准；
  - 签发时间到过期时间不超过 60 秒，留 5 秒时钟容差。
- **受众**：注册服务时显式设置 `identity_jwt_audience = urn:chrono-metaverse:api`，校验时必须一致，不依赖地址默认值。签发方和受众这两项配置缺失时，服务直接启动失败——有的 JWT 库（例如 `jose`）在这两项为空时会静默跳过检查。
- **令牌类型**：NyxID 的访问令牌和身份令牌用同一把密钥签名，签发方也相同。所以要拒绝带 `token_type` 的令牌，并要求令牌带 `nyx_service_id`。
- **服务编号**：从第一步起就校验令牌里的服务编号，要求 `nyx_service_id ∈ ALLOWED_NYX_SERVICE_IDS`。
  - 第一步填组织自定义服务的编号；注册成目录服务后（9.3 需要），把目录编号加进来，过渡期结束后删掉旧编号。
  - 别人自建连接指向本服务，一律返回 401。
- **防重放**：以令牌编号 jti 作为主键直接插入防重放集合，重复就拒绝（不能先查后写）。记录保留时间 ≥ 60 秒有效期 + 30 秒时钟容差。
- **不信任明文头**：`X-NyxID-User-*` 这类明文头一律不信任。
- **参考实现**：CMA 的 `auth/nyxid_proxy/jwt.rs`（照搬到 `api/crates/metaverse-api/src/auth/jwt.rs`）。chrono-bucket 的 `verifier.ts` 和 `nyxidAuth.ts` 没有校验服务编号，也没有做 jti 去重，这两项要自己补上。

### 9.2 谁能写：资源归属与租户隔离

**按 CMA 的实现做**（`cma/src/auth/organizations`、`layer2-core/src/resource_access`）：没有单独的"租户"实体，租户边界就是"每个空间归哪个 NyxID 主体"。身份、权限、组织成员关系和角色、agent 能做什么，都由 NyxID 给出；本服务只存"资源归哪个 NyxID 主体"这一个事实，不存人、组织、成员、钥匙或角色。

- **显式记录主人类型**：空间和组合都记 `owner: { kind: person | org, id }`。不能从一个编号去猜它是不是组织。
- **组织空间要先查证再创建**：创建组织空间时，现场调用 NyxID 的组织授权接口确认调用者是该组织的 admin，再写入 `ownerEvidence`（签发方、组织编号、核验人、核验时间，与 CMA 的组织归属证据相同）。查不到就拒绝。没有证据的空间一律按个人所有处理。
- **部署配置种子是运维行为**：演示空间可以由部署配置建（接口服务的 `METAVERSE_DEMO_SEED`，见 `infra/chrono-cd/README.md` 第 8 步），不经过任何网络接口、没有调用者。它的依据是"部署这套服务的组织 admin 把它写进了部署配置"——在 chrono-cd 里改应用规格、设密钥都要求组织 admin，所以与 admin 现场核验同级。归属证据写成单独的依据 `basis = operator_seed`、`verifiedBy = system:demo-seed`（带冒号，不可能是 NyxID 主体编号），一致性检查只在"组织主人 + 这种依据 + 证据里的组织就是配置里的主人"时接受它。种子用授权层签发的显式系统范围写入并记审计日志，只碰自己建的空间（证据是 `operator_seed`、主人一致），已有的别人的空间一律不动；建空间、第一次提交、导入任务与管理接口和 `POST /scans` 走同一条代码路径。
- **子资源继承主人**：提交、草稿、事件、物件、锚点都带 `spaceId` 和主人副本，写入时校验副本与空间的主人一致，不一致判为数据损坏（CMA 的 lineage 规则）。
- **访问级别**：

| 调用者 | 个人空间 | 组织空间 |
|---|---|---|
| 主人本人 | 管理 | — |
| 组织本身（组织的 agent key，令牌里的 sub 就是组织） | — | 管理 |
| 组织 admin | — | 管理（等同主人） |
| 组织 member | — | 只读（含内部级数据） |
| 组织 viewer | — | 只读（含内部级数据） |
| 其他人 | 无 | 无 |

  - **与 CMA 一致**：组织 admin 等同主人；member 和 viewer 只能读。日常写入由组织的 agent key（sub 就是组织）和 admin 完成。以后需要成员也能写，只改这张表对应的常量。
  - "管理"包括写入、`/api/v1/admin` 下的接口、删除空间、轮换分享令牌。
  - 这张表写成代码常量，并配测试矩阵（参照 CMA `resource_access/tests.rs`）。
- **怎么查组织角色**（CMA 的写法，chrono-cd 照抄了它）：
  - 用调用者自己的凭据调用 `GET /api/v1/orgs/{orgId}/authorization`。要求返回的编号等于 `orgId`（不认 slug），角色只能是 admin、member、viewer 三种之一。
  - 401、403、404 判为"不是成员"；其他错误判为"查不到"。整次查询有截止时间（CMA 为 15 秒）。
  - 结果不跨请求缓存，证据最多用 60 秒。写操作要求证据是在本次操作开始之后取得的。
  - 没有转发令牌时判为"查不到"。如果转发的是 JWT，要先验签，并要求它的 sub 等于身份令牌的 sub。
- **查不到怎么办**：写操作返回 503 `org_membership_unavailable`；读操作按"不是成员"处理，公开空间和凭分享令牌的访问不受影响。
- **调用者凭据从哪来（和 CMA 唯一的不同）**：
  - CMA 有网页登录，会在服务端保存用户的 NyxID 令牌，查角色时用这份令牌。本服务网站只读、不登录，没有这份令牌。
  - 所以本服务改为：在 NyxID 注册上开启"转发调用者令牌"（`forward_access_token`），让 NyxID 把调用者的令牌随请求带过来。Ornn 就是这样做的。
  - 这是一个有记录的例外：本服务会在请求期间拿到调用者的访问令牌，命令行的 agent key 配置下拿到的是 agent key 原文。
  - 约束：只在内存里用，只调这一个 NyxID 接口，不记日志、不落库、用完即弃。
  - NyxID 补上"令牌里带组织角色"（9.6）之后，就取消这个例外。
- **第一步尽量不需要转发**：
  - 所有空间归 ChronoAI 组织；
  - agent（数据源、合作方、AI 装修）一律用组织的 agent key，令牌里的 sub 就是组织，直接判为"管理"，不用查角色；
  - 只有成员用个人身份写入时，才需要转发令牌查角色。
- **不再用"组织连接的服务编号"推断成员身份**：这个推断 Ornn 和 CMA 都没有用过，只作为第 0 阶段的实测项，实测成立之前不作为授权依据。
- **功能级开关（可选）**：
  - 需要平台级限制时（例如谁能建空间），请平台管理员在 NyxID 建 `metaverse-user`、`metaverse-admin` 角色。
  - 服务端按 CMA 的做法，把令牌里的 `permissions` 按字符串精确映射成一组固定的能力；不认角色名和用户组，未知字符串和前缀通配一律不授予，不在本地维护管理员名单。
  - 第一步可以不用。
- **更细的限制交给 NyxID**：能改哪个地块、能写哪个数据源、能不能发布，由 agent key 的操作范围在转发前检查（9.3）。人的登录态不受操作范围约束，这正是上面的主人和角色检查必须存在的原因。

### 9.3 agent 的权限：NyxID agent key

- **一个 agent 一把 key**：每个 agent（Claude Code、Codex、收银系统、摄像头服务、合作方程序）用一把独立的 NyxID agent key（`nyxid_ag_` 开头），不用人的登录态。
- **key 在本地**：
  - agent 在自己的机器上运行 `nyxid login --agent-key --profile <名称>`，人在 NyxID 网页或手机上审批（可以选已有的 key，也可以新建）。
  - 凭证只保存在 agent 本机的 `~/.nyxid/profiles/<名称>/`。NyxID 服务端只存哈希，本服务完全接触不到。
- **权限在人手里**：创建 key、设置范围、轮换、吊销，都只能由人登录 NyxID 后操作。agent 不能给自己或别的 agent 扩权。
- **能限制什么**：
  - 服务范围：只允许访问本服务；
  - 操作范围：
    - 允许哪些接口（方法 + 路径模板）；
    - 路径参数的取值（例如 `space_id = restaurant`、`plot_id = p1`、`source = pos`）；
    - 请求体字段（例如事件类型只能是某几种）；
  - 有效期（默认 90 天）。

**典型配置**：

| agent | key 的主人 | 操作范围 |
|---|---|---|
| AI 装修（实体区） | 店方 | 查看接口；`/spaces/restaurant/drafts` 下的建草稿、批量操作、预览；**不含**发布（由人发布） |
| 地块合作方，或合作方的 AI | 店方组织（交给合作方使用） | `/spaces/restaurant/plots/p1/` 下的全部接口，含发布；不含其他路径 |
| 收银数据源 | 店方组织 | 只有 `POST /spaces/restaurant/sources/pos/events`，事件类型限定 |
| 花店送花 | 餐厅组织（交给花店使用） | 只有 `POST /spaces/restaurant/sources/florist/events`；事件类型只能是 `delivery.arrived`，锚点只能是收货台 |
| 店员分析脚本 | 店方 | 只有查看接口 |

**前提**：
- **需要目录服务**：路径参数和请求体的取值限制，只能挂在 NyxID 目录服务的接口上。所以本服务要注册成目录服务（需要平台管理员），并让 NyxID 同步接口列表。
- **配置开关**：配置操作范围的功能目前由一个默认关闭的开关（`assistant:operation-scopes`）控制，需要为配置的人打开。已经保存的操作范围始终生效。
- **不受影响的限制**：带操作范围的 key 不能用 WebSocket，也不能改写请求方法。本服务的写接口都是普通的 POST/PUT/PATCH，不受影响。

**AI 要用自己的 key**：
- 通过 claude.ai 连接器登录 NyxID 的 AI，用的是人的身份，拥有人的全部权限。
- 要限制 AI，必须让它用 agent key：
  - 在本地或云端会话里，用 `nyxid` 命令行的 agent key 配置调用；
  - 或者在 MCP 配置里，用 `x-api-key` 请求头带上 agent key（NyxID 的 MCP 入口只从这个头读取 agent key）。

### 9.4 服务端校验什么

**三层中间件，顺序固定**：

1. **身份**（全部 `/api/v1/*`）：按 9.1 验签。身份令牌头只能出现一次；完全不读 `X-NyxID-User-*` 明文头（Ornn 的回退是漏洞，本服务直接暴露在公网）。失败返回 401；拿不到 NyxID 公钥返回 503。
2. **功能级权限**（可选，9.2）：精确匹配 `metaverse:*` 权限字符串，不认前缀通配。
3. **资源级**（`/spaces/{space_id}/...`、`/universes/{universe_id}/...`）：读出主人，按 9.2 算出访问级别（无 / 只读 / 管理），交给后面的处理逻辑。

**请求内容与路径一致**：
- 地块路径下的每个操作（填充盒、复制目标、物件包围盒、锚点的新旧位置）都必须落在该地块内；实体区路径下的操作只能改实体区。
- 事件路径里的 `source` 就是事件的数据源，请求体里不能另填。
- 上传的用途由路径决定；地块路径下不能上传扫描。

**业务规则**：
- 基准版本；
- 草稿范围：草稿属于创建时的路径范围（实体区或某个地块），追加操作、预览、发布都必须走同一范围的路径；
- 配额：按空间和主人统计。

**数据访问层强制带授权**（避免 Ornn 出过的"按编号读取不带过滤"的越权漏洞）：
- 资源级中间件授权通过后，生成一个只有它能构造的"授权凭据"对象（包含空间编号、主人、访问级别）。
- 数据访问层所有读写都要求传入这个对象，查询条件自动带上空间编号和主人，写入条件带上主人；条件不匹配就返回 409。
- 唯一不带授权的读取是"只读主人和可见性"，专供资源级中间件使用。
- 后台任务和管理用途使用显式的"系统范围"，并且必须写审计。
- 在持续集成里加一条检查：数据访问层以外的代码不能直接访问数据库集合。
- 子集合（提交、草稿、事件、物件、锚点）都带 `spaceId`，并冗余主人字段用于索引；写入时校验它与空间的主人一致。

**返回码**：
- 看不到：返回 404，不暴露资源是否存在；
- 能看到但不能写：返回 403；
- 组织角色查不到：写操作返回 503。

本服务不保存任何钥匙，没有"钥匙表"。

### 9.5 留痕

- **记录内容**：每次提交、修订和事件都记录调用者 sub、`nyx_service_id`、路径上的作用范围（实体区、地块编号或数据源），以及由路径推断出的操作人类别。公开接口只返回操作人类别。
- **当前的缺口**：同一个主人名下的多个 agent，目前区分不开，因为 NyxID 令牌里没有 agent key 编号。在 NyxID 补上之前，靠"不同用途走不同路径"（地块、数据源）区分来源。

### 9.6 需要 NyxID 补的能力

本服务不另做替代方案；补上之前，按上文的过渡方式运行。

| 需求 | 用途 | 优先级 |
|---|---|---|
| 身份令牌加上 agent key 编号（以及子凭证编号、认证方式）。注入点在 NyxID 代理里已经能拿到这些信息，改动很小 | 留痕；区分同一主人名下的多个 agent | 高 |
| 为配置者打开"操作范围"开关（`assistant:operation-scopes`） | 第一步就要用操作范围限制 agent | 高 |
| 本服务注册成目录服务并同步接口 | 操作范围里的路径参数取值限制只能挂在目录服务的接口上 | 高 |
| 身份令牌加上调用者在相关组织的角色（或者给已注册的服务提供查询"某人在某组织的角色"的接口；目前服务账号调用组织接口会被拒绝） | 判断组织成员及角色，取消 9.2 的"转发调用者令牌"例外 | 高 |
| 提供 Claude Code / Codex 用 agent key 接入 MCP 的配置命令（目前只生成登录配置） | 让 AI 默认用受限的 agent key，而不是人的登录态 | 中 |
| 操作范围支持前缀通配（例如 `/spaces/abc/**`） | 不必逐个列接口 | 低 |
| 命令行补齐：子凭证列出和吊销 | 运维 | 低 |

## 10. 本地建造与 AI 协作

### 10.1 本地工作区

工作区是用户电脑（或云端会话）上的一个普通文件夹，由 `metaverse init <空间编号>` 创建，和平台仓库无关。用户不改平台仓库，所有修改都经接口提交。

```
餐厅/
  space.json      空间信息、区域、地块、基于哪个 seq
  palette.json    方块表
  anchors.json    锚点
  entities.json   物件
  chunks/         拉取下来的区块
  build/          建造脚本（可用 git 管理）
  assets/         网页用模型、贴图缓存
```

| 命令 | 作用 |
|---|---|
| `metaverse init` | 创建工作区，并写入技能说明 `.claude/skills/metaverse-builder/` |
| `metaverse admin …` | 管理命令：建空间、轮换分享令牌、定义区域和地块、登记事件类型、抹除事件（调用 8.4） |
| `metaverse scan <文件>` | 分片上传扫描，并发起导入和体素化任务 |
| `metaverse pull` | 下载空间的当前状态 |
| `metaverse build` | 运行建造脚本。脚本每次都从拉取的基础状态重新生成，可以反复运行 |
| `metaverse dev` | 本地查看器，和网站同一套代码；脚本改了自动刷新 |
| `metaverse shot` | 本地截图（无头浏览器软件渲染，不需要显卡），AI 直接看图自查 |
| `metaverse diff` / `check` | 和拉取时的版本对比；在本地检查改动是否都落在目标地块或实体区内 |
| `metaverse push [--plot <地块>]` | 操作写成文件 → 分片上传 → "从上传应用操作"生成草稿 → 打印草稿编号、统计和预览链接 |
| `metaverse publish <草稿编号>` | 发布草稿（所用 agent key 的操作范围要包含发布接口） |
| `metaverse voxelize` | 用和云端相同的处理镜像在本地试跑体素化，用于调参和预览，结果不直接上传（可选，需要 Docker） |

- **凭证**：
  - 人在自己的电脑上，用 `nyxid` 命令行的登录态（拥有人的全部权限）。
  - AI 在本地建造时，用自己的 agent key 配置（`nyxid login --agent-key --profile <名称>`，由人审批）。命令行用这个配置调用，不沿用人的登录态。
- **冲突**：推送冲突时，先拉取最新状态，重新运行脚本，再推送。

### 10.2 两种建造方式

| | 只用 AI 工具（不装任何东西） | 本地建造 |
|---|---|---|
| 适合 | 小改动：几个盒子、移动锚点、写事件。地块 key 可以直接发布；实体区的改动由人发布 | 大量建造、扫描处理调参 |
| 做法 | AI 直接调用"批量操作"等工具 | AI 写脚本，脚本输出操作文件，由命令行上传 |
| 自查 | 人看预览链接 | 本地截图 |

工具参数是 AI 逐字生成的，几千条操作无法通过工具参数传递，所以大改动一定要走本地建造。

### 10.3 接入说明

- **能看到工具**：用户在 Claude Code 里连上 NyxID 的 MCP，就能看到本服务的工具。工具可能要先用 `nyx__search_tools` 搜索，再用 `nyx__call_tool` 调用。
- **能写入**：调用者必须是空间主人或主人组织的成员（9.2），并且所用 agent key 的操作范围允许这个接口（9.3）。
- **技能文件**：技能说明（中文）随命令行工具分发，由 `metaverse init` 写进工作区，写明坐标约定、方块表、区域和地块规则、建造规范、两种建造方式和示例。平台仓库里的 `skills/metaverse-builder/` 只是源文件。
- **教程**：
  - `docs/tutorials/cloud-claude-code-nyxid.md` 是平台开发教程；
  - 给建造者的教程另写（`docs/tutorials/build-space.md`），内容是在本地或云端用 Claude Code / Codex 建造空间，以及怎么给 AI 配置 agent key。

## 11. 现实数据接入

- **统一接口**：`POST /api/v1/spaces/{space_id}/sources/{source}/events`，按 `sourceEventId` 去重，可以安全重试。
- **身份**：
  - 每个数据源用一把店方组织的 agent key，操作范围只允许自己那个 `source` 的事件接口，并限定事件类型。
  - 去重按"空间 + 数据源 + 数据源事件编号"进行，轮换 key 不影响去重。
- **候选数据源**：组织在 chrono-cd 上已有一个摄像头事件测试服务，配置里有"座位区"和"桌子区"，可作为第一个数据源（待定）。
- **隐私**：
  - 只接收结构化事件（某桌有人、几个人），不存画面。
  - 事件分公开和内部两级；公开接口只返回事件类型登记的公开字段。

## 12. 多空间组合与跨空间事件

- **创建与修改**：第一步，组织成员都能创建组合，创建者是组合的主人。修改名称、可见性、摆放和连接，需要 NyxID 身份是组合主人。
- **加入与退出**：
  - 把空间加入组合，必须由该空间的主人（或主人组织成员）调用加入接口，所以别人不能把你的空间拉进他的组合。
  - 空间主人随时可以让本空间退出。
  - 加入和退出都记为组合的修订。
- **可见性**：组合不能比任何成员更公开——有凭链接查看的成员时，组合也只能凭链接查看。凭组合的分享令牌可以读取各成员空间的公开数据（8.2）。
- **连接**：连接两端只能引用公开锚点。
- **送花示例**：
  - **两条事件**：花店在自己的空间写一条 `delivery.sent`（显示为路线起点），餐厅收到后写一条 `delivery.arrived`（显示为路线终点）。两条用同一个 `correlationId = "<花店空间编号>:<编号>"`。
  - **防伪造**：起点事件只能写在前缀对应的空间里，其他空间无法伪造。
  - **配对规则**：路线只在当前组合的成员之间配对。同一 `correlationId` 下，取起点事件和终点事件（更正已应用；同一侧有多条时取最新一条），在组合坐标系里从起点锚点画到终点锚点，动画时长取两条事件的时间差。
  - **路线画法**：成员之间有连接时，路线沿连接走最短路径，经过每条连接两端的锚点；没有连接就画弧线。
  - **不完整时**：只有起点、还没有终点时，只在起点显示图标；单空间视图只显示本空间这一侧的图标。
  - **由花店代写终点**：如果终点事件要由花店来写，餐厅可以在 NyxID 里创建一把组织 agent key 交给花店，操作范围只允许往餐厅的 `florist` 数据源写 `delivery.arrived`，锚点只能是收货台（9.3）。

## 13. 存储（MongoDB）

### 13.1 基础

- **数据库**：chrono-cd 的 MongoDB 插件——共享的 Atlas 集群，MongoDB 8，副本集，支持事务。
- **私有地址**：数据库地址只有集群内能访问，所以建索引和迁移由接口服务自己执行：
  - 启动时先幂等地建索引（多副本同时执行也安全，几秒内完成），建完才让 `/api/healthz` 返回 200。唯一索引是并发控制和去重的前提。
  - 耗时的数据迁移不放在启动路径上：在后台执行，用 `migrations` 集合里带租约的锁保证只有一个副本在跑；依赖它的写接口在迁移完成前返回 503。
  - 迁移必须新旧版本兼容（先扩后收），因为滚动更新时新旧副本同时运行。
- **容量与备份**：数据库占用不计入 chrono-cd 配额，但这是共享集群。需要先向平台团队确认容量预期和备份策略。
- **可替换**：大文件存储做成一层接口，可以换成对象存储，业务代码不用改。

### 13.2 集合

| 集合 | 内容 | 主要索引 |
|---|---|---|
| `spaces` | 空间（含区域、地块的当前状态） | `_id`、`(owner.kind, owner.id, updatedAt)` |
| `commits` | 提交 | `(spaceId, seq)` 唯一、`(spaceId, at)`、`jobId` 部分唯一 |
| `chunks` | 区块（压缩存储），带 `publishedAt` | `_id` = 区块哈希 |
| `draftChunks` | 草稿区块 | 随草稿过期 |
| `records` | 物件和锚点的各个版本 | `_id` = 内容哈希 |
| `stateBlobs` | 关键帧状态清单、区域清单 | `_id` = 内容哈希 |
| `palettes` | 方块表版本 | `_id` = 内容哈希 |
| `entities` / `anchors` | 当前状态（读缓存） | `(spaceId, id)` 唯一 |
| `assetRefs` | 资源被哪些空间引用 | `(hash, spaceId)` |
| `events` | 现实事件 | `(spaceId, at)`、`(spaceId, recordedAt)`、`(spaceId, corrects)` 稀疏、`(spaceId, source, sourceEventId)` 唯一 |
| `stateSnapshots` | 状态类事件的定期快照 | `(spaceId, at)` |
| `eventTypes` | 事件类型版本 | `(spaceId, type, version)` 唯一 |
| `drafts` / `previews` | 草稿、预览令牌（只存哈希） | `spaceId`；按过期时间清理 |
| `uploads` / `jobs` | 上传会话、任务 | 见 6.1、6.4 |
| `universes` / `universeRevisions` | 组合当前状态、修订 | `(universeId, seq)` 唯一、`(universeId, at)` |
| `replay` | 令牌防重放 | `_id` = jti，按过期时间删除 |
| `migrations` | 迁移记录与锁 | `_id` = 迁移名 |
| GridFS `assets` | 原始扫描、网页用模型、贴图、大块操作、脚本 | `files.filename` 唯一（= 内容哈希） |

### 13.3 事务

事务只包含：提交记录、空间指针、物件和锚点的当前状态、资源引用（`assetRefs`）；由任务产生的提交，还包括该任务的状态更新。区块、方块表和大对象在事务前按内容哈希幂等写入（5.7）。

### 13.4 例外：法律删除

出于法律要求删除个人信息时，由管理员物理清除相关内容（事件内容，必要时包括扫描资源），并在时间线上留一条不含内容的清除记录。被清除的资源返回 410。

## 14. 部署（chrono-cd）

部署在 ChronoAI 组织下：项目 `metaverse`，应用 `chrono-metaverse`。在组织下部署、写密钥、重启都要求操作者是组织的 admin。新应用的主机名在 `apps.nyxid.ai` 下，以创建后返回的 `url` 为准。只有一个应用密钥：演示空间的分享令牌 `METAVERSE_DEMO_SHARE_TOKEN`（规格的 `secret_keys` 声明名字，值用 `set_app_secrets` 设置，接口服务只存哈希，9.2）；数据库连接由插件注入，身份令牌只用公钥校验。

| 服务 | 镜像 | 路由 | 暴露 | 说明 |
|---|---|---|---|---|
| `metaverse-web` | `ghcr.io/chronoaiproject/chrono-metaverse-web` | `/` | 公网 | 静态网站（nginx 非特权镜像，端口 8080）；健康检查 `/healthz` |
| `metaverse-api` | `ghcr.io/chronoaiproject/chrono-metaverse-api` | `/api` | 公网 | 健康检查 `/api/healthz`；挂 MongoDB 插件；axum（hyper）默认没有空闲超时，不会比平台更早断开连接 |
| `metaverse-worker` | `ghcr.io/chronoaiproject/chrono-metaverse-worker` | — | 只在集群内（`expose: internal`，不进公网路由） | 只开健康检查端口（`/healthz`）给平台探针；进程内设看门狗，任务心跳停滞就退出重启；体素化放在子进程里；内存申请 3Gi，上限 8Gi（按实测峰值调整） |

- **服务名**：chrono-cd 要求服务名在同一主人（ChronoAI 组织）的所有应用之间唯一，`web`、`worker` 已被组织里的其他应用占用，所以加 `metaverse-` 前缀。服务之间按 `http://<服务名>:<端口>` 互相访问（网站的 nginx 把 `/api/` 转给 `http://metaverse-api:8080`）。规格文件和部署步骤见 `infra/chrono-cd/`。
- **镜像要求**：只能用 ghcr.io，建议设为公开包；用数字形式的非 root 用户（如 `USER 1000:1000`）；构建 linux/amd64。
- **滚动更新**：每次多起一个新副本、旧副本先不下线，终止宽限 30 秒，更新期间新旧副本会同时运行。处理服务收到停止信号后不再领新任务，做不完的任务等租约过期后由其他副本重做；任务必须幂等（6.4）。
- **配额**：
  - 组织配额由组织下所有应用共用，默认 8 核 / 16Gi / 40 个容器 / 80Gi。
  - 计算方式：Σ(副本数 × 资源申请)，另外为滚动更新预留本应用资源申请最大的那个服务一份，再加 1 个容器。
  - 部署前先查用量，不够就提配额申请。
- **持续集成**：GitHub Actions 构建并推送镜像（`.github/workflows/images.yml`）；目前由组织 admin 用 chrono-cd 的 `PATCH` 更新镜像版本（`infra/chrono-cd/README.md`），以后可以在工作流里用组织的 NyxID API key 自动调用。
- **注册到 NyxID**：
  - 第一步：组织管理员自助注册自定义服务，地址填应用根地址，OpenAPI 地址填 `https://<应用域名>/api/openapi.json`（只包含 `/api/v1/*`，不含管理接口，`paths` 带 `/api` 前缀），开启身份令牌并设置 `identity_jwt_audience`（9.1）。具体命令见开发教程第 9 节。
  - 要用 agent key 的路径参数限制时（第 3 阶段之前就需要，9.3）：请平台管理员注册成目录服务，并同步接口列表；同时为配置操作范围的人打开 `assistant:operation-scopes` 开关。

## 15. 平台核查结论

| 项目 | 结论 | 对设计的影响 |
|---|---|---|
| chrono-cd 公网路由 | 直接暴露，前面没有 NyxID | 自己校验身份令牌（9.1） |
| chrono-cd 与 NyxID 注册 | 不会自动注册 | 手动注册（14） |
| chrono-cd 镜像 | 只能用 ghcr.io；必须用数字 uid | 见 14 |
| chrono-cd 运行 | 负载均衡超时 300 秒、网络层约 100 秒；存活探针每 15 秒检查、超时 5 秒；滚动更新时新旧副本并存；没有定时任务、没有显卡 | 长操作做成任务；处理服务不暴露并自带看门狗；清理放在处理服务的循环里；截图在本地做 |
| MongoDB 插件 | 共享 Atlas、MongoDB 8；不计配额；文档没写备份 | 向平台确认（13.1） |
| NyxID 身份令牌 | 含用户编号、全局角色、权限、服务编号、jti；不含 agent key 编号；用户可以给自己的连接随意设置受众 | 固定服务编号、jti 去重；区分 agent 要靠 NyxID 补字段（9.6） |
| NyxID agent key | 没有单独的 agent 实体，agent key 就是一把受限的 API key（`nyxid_ag_` 开头），是不记名凭证，只在 agent 本机保存；创建、配置、轮换、吊销都只能由人登录后操作；agent 通过 `nyxid login --agent-key` 经人审批拿到子凭证，子凭证随父 key 一起失效 | 每个 agent 一把 key（9.3） |
| NyxID 下游识别 agent | 代理转发时令牌里没有 key 编号，自定义请求头被丢弃；只有"下游拿到原始 key 再去 NyxID 查询"这一种办法，本服务不采用（会让服务端持有用户凭证） | 留痕按路径范围，等 NyxID 补字段（9.5、9.6） |
| NyxID 签名能力 | 不给 agent 发密钥对，也不代 agent 签名 | 不做签名方案，完全依赖 NyxID 的凭证和操作范围 |
| NyxID 组织接口 | `GET /api/v1/orgs/{id}/authorization` 用调用者自己的凭据查询角色；服务账号调用组织接口会被拒绝；身份令牌里没有组织角色 | 查角色要转发调用者令牌（9.2 的例外），并向 NyxID 提需求（9.6） |
| Ornn / CMA 的租户隔离 | 都没有"租户"实体，靠资源主人字段加实时查询组织角色。CMA 显式记录主人类型、严格验签、不跨请求缓存；Ornn 只解码不验签、有明文头回退、按编号读取不带过滤，出过越权漏洞 | 照 CMA 的模型做，数据访问层强制带授权（9.2、9.4） |
| NyxID 角色 | 全局；自定义角色只能由平台管理员创建 | 空间级权限在本服务内实现 |
| NyxID 操作范围 | 可以限定 agent key 能调的接口、路径参数取值和请求体字段，在转发前拦截；配置开关默认关闭，只能由人配置；参数限制需要目录服务；不支持通配 | agent 细粒度权限的唯一手段（9.3）；接口路径为此设计（8.3） |
| NyxID 代理 | 请求头和响应头都走白名单；请求体上限 100MB；AI 工具只能返回文本或小图片 | 8.5 |
| chrono-bucket（即存储服务 Chrono Storage Service） | 需要 `chrono-bucket-user` 角色；按版本号写入有覆盖问题；不支持分段下载；没有前缀列表 | 不用：已决定全部数据（含大文件）存 MongoDB 插件；13.1 的"可替换"只是容量不够时的预案 |
| NyxID 生成 AI 工具 | `operationId` 转小写、非字母数字换成 `_`；用注册地址拼 `paths`，不看 `servers` | 接口命名和路径写法见 8.3 |
| 网络层缓存 | 不缓存没有扩展名的路径；租户不能配置缓存规则 | 接口进程内加缓存，并限流（8.2） |

## 18. 风险

| 风险 | 应对 |
|---|---|
| 平台不希望在共享数据库里放大文件，或容量不够 | 大文件存储做成接口层，可以换成对象存储 |
| AI 用人的登录态（例如 claude.ai 连接器）时，拥有人的全部权限 | AI 一律用自己的 agent key，并配置操作范围（9.3） |
| 操作范围的配置开关默认关闭，参数限制需要目录服务 | 第 0 阶段就协调平台管理员打开开关、注册目录服务（9.6） |
| 扫描质量差（噪点、缺面、玻璃反光） | 清理步骤；人工微调对齐；用扩展层修补 |
| 重扫配准不准，扩展层和锚点错位 | 只用稳定结构配准；超过阈值转人工；实测误差 |
| 公开接口被刷 | 限流、分页上限、内容不变的数据走永久缓存 |
| NyxID 令牌里看不到 agent key | 暂时按路径范围留痕；向 NyxID 提需求，把 agent key 编号加进令牌（9.6） |
| 部署打断长任务 | 租约加幂等重做（6.4） |
| 组织配额被同组织其他应用占满 | 部署前查用量，必要时申请配额 |
| 上传的模型是恶意构造的（解压炸弹等） | 解析前检查、子进程内存上限和超时；物件模型重新导出后才能使用 |
