# chrono-metaverse 整体设计

> 状态：方案稿（讨论中）。标注"待定"的地方需要确认后再实现。
> 平台相关结论均来自对 NyxID、chrono-cd、chrono-bucket 源码的核查，见第 15 节。

---

## 1. 目标与范围

### 1.1 要做什么

1. **实体餐厅的数字孪生**：导入 Scaniverse 扫描的模型（glb 等），自动生成"方块化"的优化模型（类似 Minecraft 的网格，贴图取自原模型）。
2. **开放虚拟位置**：在孪生的基础上扩展出现实中不存在的虚拟区域，划成地块，按钥匙授权给合作方或 AI 建造。
3. **一条时间线**：空间的每一次变化、店里发生的每一件现实事件都按时间记录，网站可以回放到任意时刻。
4. **三种视图**：原始模型 / 优化模型 / 优化模型 + 虚拟扩展。
5. **多空间组合**：多个空间（餐厅、花店……）可以拼在一起展示，跨空间事件（送花）同步回放。
6. **权限钥匙**：每个空间可以签发带特定权限的钥匙，用来通过接口更新数据。
7. **NyxID 服务**：用 NyxID 鉴权，注册成 NyxID 服务；AI（Claude Code / Codex）通过 NyxID 调用接口。部署在 chrono-cd，数据存 MongoDB。

### 1.2 明确不做

- **不是多人游戏**：没有化身、没有多人实时同步。
- **不做网页编辑器**：网站是只读的，所有人只能看。
- **不做分支**：只有一条时间线。
- **不自己实现 MCP**：只提供 OpenAPI 文档，由 NyxID 自动生成 AI 工具。

### 1.3 核心原则

- **读写分离**：读是公开的，走网站和只读接口；写只能走写接口，必须经过 NyxID 鉴权并持有空间钥匙。
- **只追加**：所有数据都只追加，不修改、不删除历史。录错了就追加一条更正。
- **一切修改皆入时间线**：每次修改都记录操作人、钥匙和时间。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 空间 | 一个独立的方块世界，有自己的坐标系、格子尺寸和方块库。例："某某餐厅" |
| 实体区 | 空间中与现实一一对应的部分，由扫描生成，只有店方能校正 |
| 虚拟区 | 空间中现实不存在的扩展部分，视觉上与实体区明确区分 |
| 地块 | 虚拟区内划出的一块范围，可以单独授权 |
| 图层 | 每个空间分三层：扫描层（原始模型）、基础层（由扫描自动生成的方块）、扩展层（人和 AI 的修改，可覆盖基础层） |
| 区块 | 空间按 32×32×32 格切分的存储和渲染单位 |
| 方块库 | 通用方块（石、木、玻璃……）加上从扫描贴图提取的专属方块 |
| 物件 | 非方块的东西：一束花、家具模型等，带位置和自定义属性 |
| 锚点 | 现实对象在孪生里的位置标注：桌号、座位、区域、门、摄像头 |
| 提交 | 一组空间修改，是时间线上的一个点 |
| 事件 | 一条现实发生的事：入座、出餐、送达……挂在锚点上 |
| 草稿 | 还没发布到时间线的修改，供预览确认 |
| 空间钥匙 | 本服务签发的权限凭证，限定能对哪个空间做什么 |
| 组合宇宙 | 引用多个空间并规定它们的摆放位置 |

## 3. 总体架构

```
   写（只能走接口）                                      读（所有人）
 Claude Code / Codex  ─┐                              浏览器网站（只读查看器）
 命令行工具 / 脚本     ─┤                                       │
 收银 / 摄像头等数据源 ─┤                                       │
                       ▼                                       │
          NyxID（登录鉴权、身份令牌、钥匙代管注入）            │
                       │                                       │
                       ▼                                       ▼
        ┌──────────── 接口服务（Bun + Hono）──────────────────────┐
        │  写接口 /api/v1/*：校验 NyxID 身份令牌 + 空间钥匙        │
        │  读接口 /api/public/*：无需登录，只返回公开数据，可长缓存 │
        └──────────────┬───────────────────────┬─────────────────┘
                       │ 任务表                 │ 截图请求
                       ▼                        ▼
             处理服务（Python）           渲染服务（无头浏览器）
             对齐 / 体素化 / 取色 /       与网站同一套渲染代码，
             生成网页用模型               给 AI 和预览出图
                       │                        │
                       └──────► MongoDB ◄───────┘
                     （普通集合 + GridFS 大文件）

   全部服务 + MongoDB 插件部署在 chrono-cd（ChronoAI 组织）
```

| 组件 | 技术 | 职责 |
|---|---|---|
| 网站 | TypeScript + Three.js | 只读 3D 查看器：视图切换、时间轴回放、"现在"模式 |
| 接口服务 | Bun + Hono + @hono/zod-openapi | 读写接口、鉴权、钥匙、时间线、上传、任务调度 |
| 处理服务 | Python（trimesh / open3d / numpy） | 扫描对齐、体素化、取色、压缩模型与多级细节 |
| 渲染服务 | Node + Playwright（无头 Chromium） | 用网站同一套渲染代码出截图，给 AI 自查和草稿预览 |
| 核心包 | TypeScript | 操作定义、区块结构、时间线回放引擎，前后端共用 |
| 工具包 / 命令行 | TypeScript | 生成批量操作、分片上传、数据源接入 |

## 4. 数据模型

### 4.1 空间

```
spaces {
  _id: "restaurant-xyz"          // 空间编号（小写字母、数字、连字符）
  name, description
  ownerSub                        // NyxID 用户编号
  visibility: public | unlisted   // 公开 / 仅知道链接可看（待定：是否需要 private）
  voxelSize: 0.1                  // 每格边长（米），创建后不可改（待定：默认值）
  head: { seq, commitId, at }     // 时间线最新位置
  regions: [ { id, kind: physical | virtual, name, boxes: [[x0,y0,z0,x1,y1,z1]] } ]
  plots:   [ { id, regionId, name, boxes, holder } ]   // 地块（只在虚拟区内）
  createdAt
}
```

- 坐标：整数格坐标，y 轴向上，1 格 = `voxelSize` 米；原点在实体区地面的一个角。
- 区域和地块的变更本身也是时间线操作（可回放）。

### 4.2 图层与区块

- 每个空间有三层：
  - **扫描层**：原始模型文件的引用，加上对齐变换。
  - **基础层**：由扫描自动生成，只出现在实体区。
  - **扩展层**：手工和 AI 的修改。
- **扩展层优先**：扩展层的格子可以放方块，也可以是"空气覆盖"（删除基础层的方块）。因此重新生成基础层不会冲掉手工修改。
- **区块**：每个区块是 32³ 个 16 位方块编号，压缩后按内容 SHA-256 存储。相同内容只存一份，历史版本之间共享。

### 4.3 方块库

```
palettes { _id: hash, blocks: [ { id, name, kind: solid|glass|emissive|…,
           texture: { top, side, bottom } | color, tags } ] }
```

- 通用方块随系统提供。
- 扫描生成的专属方块（"餐厅地砖-03"）的纹理来自原贴图的截取，存成资源文件。

### 4.4 物件

非方块的模型，记录模型资源哈希、位置/旋转/缩放、所属区域和自定义属性，例如一束花或一盏吊灯。

### 4.5 锚点

```
anchors { spaceId, anchorId: "table-03", kind: table|seat|zone|door|camera|counter,
          box | position, label, visibility: public|internal }
```

事件引用锚点编号，不直接写坐标。重新装修后只需移动锚点，历史事件仍然能正确显示在对应位置。

### 4.6 组合宇宙

```
universes { _id, name, visibility,
            members: [ { spaceId, offset: [x,y,z], rotation: 0|90|180|270 } ],
            links:   [ { from: {spaceId, anchorId}, to: {spaceId, anchorId}, kind: door|portal|street } ] }
```

- 组合只引用空间，不复制空间。
- 摆放用整格偏移加 90° 旋转，保证各空间的网格对齐。
- 组合本身的变更也有自己的时间线。

## 5. 时间线

### 5.1 两类数据，一条时间线

| | 空间变化 | 现实事件 |
|---|---|---|
| 例子 | 导入扫描、生成方块、装修、建虚拟地块、移动锚点 | 入座、点单、出餐、花送达、营业状态 |
| 频率 | 低（一天几次） | 高（一天成百上千条） |
| 存储 | 提交 + 区块快照 | 事件流 |
| 显示 | 改变 3D 场景本身 | 在锚点上做可视化（亮起、图标、热力图、轨迹） |
| 时间 | 提交时间 | 事件发生时间（可能晚到，按发生时间排序） |

### 5.2 提交

```
commits {
  _id, spaceId, seq,              // seq 在空间内严格递增（唯一索引）
  at,                             // 生效时间
  actor: { sub, keyId, keyName, purpose },
  message,                        // 例："AI：二楼虚拟露台"
  ops: [...] | opsRef,            // 本次操作（过大时单独存）
  changedChunks: [ { layer, cx, cy, cz, hash } ],
  keyframe?: { manifest }          // 每 50 次提交存一份完整区块清单
  scriptSource?                    // AI 生成操作时附带的脚本原文（只为追溯）
}
```

- **跳到某一时刻**：找到这个时刻之前最近的关键帧，再叠加之后各次提交的区块变化。
- **耗时计算的结果直接存档**：例如体素化记录"参数 + 结果区块"，回放时直接读结果，不重新计算。
- **重扫**：同一家店隔月重扫，追加一次"导入扫描 + 重新生成基础层"，时间线上就能看到真实变化。

### 5.3 现实事件

```
events {
  spaceId, at, recordedAt,
  source,                 // 数据源名称，例 "pos" / "frigate"
  sourceEventId,          // 数据源自己的编号，(spaceId, source, sourceEventId) 唯一，用来去重
  type,                   // 例 "table.occupied" / "order.served" / "delivery.arrived"
  anchorId, data,
  visibility: public | internal,
  correlationId?,         // 跨空间关联，例：同一次送花
  corrects?               // 更正哪一条事件
}
```

- **事件类型**：每个空间登记自己的事件类型，写明数据格式、默认可见级别和显示方式。
- **只追加**：录错了就追加一条 `corrects` 指向原事件的更正，回放时以更正为准。

### 5.4 回放与"现在"模式

- **回放**：拖到任意时刻 T，场景显示 T 时的空间样子，事件显示 T 附近一个时间窗内的内容。支持按小时或按天快进，比如看一整天的客流。
- **"现在"模式**：自动跟随最新数据。网站每隔几秒拉取一次新提交和新事件。这只是展示最新数据，不是多人同步。
- **组合回放**：按同一时刻取各空间对应的版本。跨空间事件凭 `correlationId` 关联，两边同时显示。

### 5.5 草稿

- **草稿**是还没发布的修改，记录它基于哪个时间线位置（`baseSeq`）。草稿不进时间线，也不算第二条时间线。
- **自查**：AI 修改后调用截图接口自己检查。
- **人工确认**：需要人看时，生成一个有有效期的预览链接，在网站里以只读方式打开。
- **发布**：草稿发布成一次提交。如果在此期间时间线已经前进，而且改到了同样的区块，就返回冲突，由调用方在最新位置上重做。

### 5.6 并发控制

写入方很少（店方、AI、数据源），不需要复杂的合并：
- **提交**：在一个 MongoDB 事务里完成三件事：写入新区块、插入提交（seq 唯一）、按 `head.seq == 旧值` 条件推进空间指针。
- **基准位置**：调用方用 `baseSeq` 或 `If-Match` 说明自己基于哪个位置。位置已经变了就返回 409。

## 6. 扫描处理流程

处理服务从任务表领取任务，异步执行。每一步的参数和结果都记入时间线。

1. **上传**：分片上传（每片不超过 32MB），完成后校验整体 SHA-256，存入 GridFS。
2. **对齐**：
   - 用平面拟合找到地面，按重力方向摆正。
   - 把主墙方向转到网格轴向，否则体素墙会出现锯齿。
   - 对齐变换可以通过接口手动微调。
3. **体素化**：按空间的 `voxelSize` 把网格模型转成格子。只处理实体区范围。
4. **取色和贴图**：
   - 每个格子从原贴图采样颜色。
   - 在感知色彩空间里把颜色聚成 N 种方块（默认 64 种）。
   - 每种方块从原贴图截一块代表性纹理。
   - 结果看起来像原模型，但已经是程序生成的方块。
5. **清理**：去掉漂浮的方块，补小洞，平滑噪点。
6. **网页用模型**：为原始模型生成压缩版和多级细节版本，供网站的"原始"视图使用。
7. **后期：语义识别**：AI 通过截图识别地板、墙、桌椅，替换成规整的结构或预制件。

格式支持：第一版只支持网格模型（glb / obj）。高斯点云（Scaniverse 的 spz / ply）放到后期做（待定）。

## 7. 网站（只读查看器）

- **视图**：
  - 原始：扫描模型。
  - 优化：基础层加实体区的修正。
  - 优化 + 扩展：再加上虚拟区。
  - 混合：扫描范围内显示原始模型，范围外显示方块。
  - 叠加对比：原始模型半透明叠在方块上。
  - 剖切：去掉屋顶或墙，看室内。
- **虚拟区标识**：虚拟区有统一的视觉标识，比如边界光效和"虚拟"标签，避免被误认为现实存在。
- **时间轴**：
  - 在时间轴上标出提交，并显示事件密度。
  - 可以播放、暂停、调速、跳转。
  - 有"现在"按钮，切回实时跟随。
- **事件可视化**：桌子占用时高亮，出餐时冒出图标，送达时显示路线，也可以叠加客流热力图。
- **加载**：区块和模型按内容哈希命名，网站会长期缓存它们。区块网格在浏览器后台线程里生成。

## 8. 接口设计

### 8.1 两组接口

| | 读接口 `/api/public/*` | 写接口 `/api/v1/*` |
|---|---|---|
| 鉴权 | 无 | NyxID 身份令牌 + 空间钥匙 |
| 访问方式 | 直接访问应用域名 | 经过 NyxID 代理（AI 走 NyxID 自动生成的工具） |
| 返回内容 | 只含公开空间、公开锚点和公开事件 | 按钥匙权限决定 |
| 缓存 | 内容寻址的资源设为永久缓存 | 不缓存 |

### 8.2 读接口

| 接口 | 说明 |
|---|---|
| `GET /api/public/spaces/{spaceId}` | 空间基本信息、区域、公开锚点 |
| `GET /api/public/spaces/{spaceId}/snapshot?at=` | 某一时刻的区块清单、方块库、物件、扫描引用 |
| `GET /api/public/spaces/{spaceId}/timeline?from=&to=` | 时间段内的提交列表 |
| `GET /api/public/spaces/{spaceId}/events?from=&to=&types=` | 时间段内的公开事件 |
| `GET /api/public/chunks/{hash}` | 区块二进制，永久缓存 |
| `GET /api/public/assets/{hash}` | 模型或贴图，支持分段下载（Range），永久缓存 |
| `GET /api/public/universes/{id}?at=` | 组合宇宙 |
| `GET /api/public/previews/{token}` | 草稿预览（带有效期的令牌） |

### 8.3 写接口（也是 AI 工具）

每个接口的 `operationId` 会成为 AI 工具名（`chrono-metaverse__<operationId>`），描述要写清楚用途和限制。

| 分组 | 接口 |
|---|---|
| 空间管理 | 创建空间、修改基本信息、定义区域和地块、签发/吊销钥匙 |
| 上传 | 创建上传 → 逐片上传 → 完成上传（只供命令行和数据源使用，AI 不直接传大文件） |
| 扫描 | 导入扫描、发起体素化任务、调整对齐、查询任务进度 |
| 查看（给 AI） | 区域内容（按层用文字列出）、空间统计、截图（返回 PNG，AI 可以直接看到） |
| 修改 | 创建草稿 → 批量操作（放置、填充、空心盒、替换、复制区域、放物件、移动锚点）→ 截图自查 → 发布 |
| 事件 | 批量写事件（每批最多 1000 条，按数据源编号去重）、登记事件类型、更正事件 |
| 组合 | 创建或修改组合宇宙、连接 |

### 8.4 NyxID 代理带来的约束

- **自定义请求头会被丢掉**：空间编号、基准位置、钥匙等都放在路径、查询参数或请求体里。允许使用的标准头有 `If-Match`、`Idempotency-Key`、`Range`。
- **请求体上限**：经 NyxID 单次请求最大 100MB；走 AI 工具时二进制要转 base64，实际约 75MB。所以大文件一律分片上传。
- **AI 工具的返回**：返回内容会被转成文本。图片只有 PNG/JPEG 且不超过 5MB 时才会作为图片返回，所以截图接口要控制尺寸。
- **超时**：前面的网络层大约 100 秒没有响应就会断开，所以体素化、截图批处理等耗时操作一律做成异步任务。

### 8.5 AI 怎么建造

- **不在服务器上执行 AI 写的代码**。AI 在自己的环境里用工具包写脚本，脚本生成批量操作，再调用"批量操作"接口提交。
- **脚本留档**：脚本原文可以作为附件存档，只用于追溯。
- 这样服务器不需要隔离执行环境，也就没有代码注入风险。

## 9. 鉴权与权限

### 9.1 NyxID 身份令牌

接口服务部署在 chrono-cd 上，公网可以直接访问，前面没有 NyxID 把关。所以写接口必须自己校验 NyxID 注入的 `X-NyxID-Identity-Token`：
- **签名与令牌格式**：用 NyxID 的公钥列表（JWKS）校验签名，只接受 RS256。签发方（iss）以 NyxID 的 `/.well-known/openid-configuration` 为准。受众（aud）必须等于本服务在 NyxID 登记的受众。令牌有效期为 60 秒。用户编号（sub）不能为空。
- **服务编号**：注册成 NyxID 平台目录服务后，把令牌里的服务编号（`nyx_service_id`）固定成本服务的编号。
- **防重放**：按令牌编号（jti）在 2 分钟内去重。
- **不信任明文头**：绝不信任 `X-NyxID-User-*` 这类明文头。
- **参考实现**：可以照搬 chrono-bucket 的 `src/auth/verifier.ts` 和 `src/middleware/nyxidAuth.ts`。

### 9.2 为什么还需要空间钥匙

核查确认 NyxID 有两个限制：
- 令牌里**不包含是哪个 API key 或哪个 agent 发起的调用**，只能知道是哪个用户。
- NyxID 的权限是全局角色，**无法做到"某人只能改某个空间的某个地块"**。NyxID 的按接口限制功能需要人工配置，而且由默认关闭的功能开关控制，不适合用来做空间钥匙。

所以按空间的权限和钥匙在本服务内实现。写操作需要两样东西同时满足：
- **NyxID 身份**：确定是谁在操作。
- **空间钥匙**：确定这次能做什么。

### 9.3 空间钥匙

```
keys {
  _id: keyId, spaceId, name, purpose: admin | feed | plot | ai | viewer
  secretHash,                      // 只存哈希，明文只在创建时显示一次
  scope: {
    actions: [ "voxel.write", "entity.write", "anchor.write", "event.write", "scan.import", "draft.publish", … ],
    plots?: [ plotId ], regions?: [ regionId ], layers?: [ "ext" ],
    eventTypes?: [ … ], maxVisibility?: public | internal
  },
  allowedSubs?: [ sub ],           // 可选：只允许这些 NyxID 用户使用
  quota: { opsPerDay, eventsPerDay },
  expiresAt, createdBy, revokedAt
}
```

| 钥匙用途 | 发给谁 | 典型权限 |
|---|---|---|
| 店方管理 | 自己 | 全部，包括签发钥匙 |
| 数据接入 | 收银、摄像头事件服务、预订系统 | 只能写指定类型的事件 |
| 虚拟地块 | 合作方、AI | 只能改自己地块内的方块和物件，只能写扩展层 |
| AI 装修 | Claude Code / Codex | 只能建草稿；发布需要另外的权限 |

- **钥匙怎么传**：
  - **首选**：把钥匙存进 NyxID，作为这个服务的连接凭证，由 NyxID 在转发时注入，AI 拿不到明文。注入的头能否到达下游，需要在第 0 阶段实测。
  - **备选**：放在请求体的 `spaceKey` 字段里。
- **留痕**：每次提交和事件都记录 NyxID 用户、钥匙编号、钥匙名称和用途。这样能区分"AI 装修钥匙"和"收银系统"，弥补 NyxID 令牌里看不到 key 的问题。
- **创建空间**：只允许配置里列出的 NyxID 用户（`ADMIN_SUBJECTS`）创建空间。以后可以改成 NyxID 全局权限 `metaverse:space:create`，权限名要带前缀，避免和其他服务的同名权限冲突。

## 10. AI 协作

- **接入**：用户在 Claude Code 或 Codex 里连上 NyxID 的 MCP，就能看到本服务的工具，不需要额外配置。
- **典型流程**：
  1. 用"区域内容"和"截图"了解现状。
  2. 创建草稿。
  3. 在本地写脚本，生成批量操作。
  4. 提交批量操作。
  5. 截图自查，不满意就继续修改。
  6. 生成预览链接给人看。
  7. 确认后发布（或者由持有发布权限的人来发布）。
- **技能文件**：仓库里放一份 Claude Code 技能说明（`skills/metaverse-builder/`），写明坐标约定、方块库、区域和地块规则、建造规范和常见示例。

## 11. 现实数据接入

- **统一接口**：所有数据源走同一个"批量写事件"接口，用数据源编号去重，可以安全重试。
- **鉴权**：数据源也是机器，经 NyxID 调用（用 NyxID 服务账号或 API key），并持有一把"数据接入"钥匙。
- **候选数据源**：ChronoAI 组织在 chrono-cd 上已经有一个摄像头事件测试服务（配置里有"座位区""桌子区"）。如果是同一个项目，可以作为第一个数据源（待定）。
- **隐私**：
  - 只接收结构化事件（某桌有人、几个人），不存画面。
  - 事件分公开和内部两级，只读网站只显示公开级（待定：分级标准）。

## 12. 多空间组合与跨空间事件

- 组合宇宙按 4.6 节的方式引用多个空间，所有组合都可以在网站上公开查看。
- **送花示例**：花店写一条"送出"事件，餐厅写一条"送达"事件，两条共用同一个 `correlationId`。回放时，在组合视图里显示一条从花店到餐厅的路线动画。
- **跨主人**：餐厅可以给花店签发一把只能往"收货台"锚点写"送达"事件的钥匙。

## 13. 存储（MongoDB）

使用 chrono-cd 的 MongoDB 插件：共享的 Atlas 集群，MongoDB 8，副本集，支持事务。

| 集合 | 内容 | 主要索引 |
|---|---|---|
| `spaces` | 空间 | `_id` |
| `keys` | 空间钥匙 | `spaceId`、`secretHash` |
| `commits` | 提交 | `(spaceId, seq)` 唯一、`(spaceId, at)` |
| `chunks` | 区块（压缩二进制，约几 KB） | `_id` = 内容哈希 |
| `palettes` | 方块库 | `_id` = 内容哈希 |
| `anchors` | 锚点当前状态（历史在提交里） | `(spaceId, anchorId)` |
| `events` | 现实事件 | `(spaceId, at)`、`(spaceId, source, sourceEventId)` 唯一 |
| `eventTypes` | 事件类型登记 | `(spaceId, type)` |
| `drafts` | 草稿 | `spaceId` |
| `uploads` | 分片上传会话 | 设有过期时间 |
| `jobs` | 任务表（处理服务按租约领取） | `(status, createdAt)` |
| `universes` | 组合宇宙 | `_id` |
| `replay` | 令牌防重放 | 2 分钟后过期 |
| GridFS `assets` | 原始扫描、网页用模型、贴图、截图 | 文件名 = 内容哈希 |

- **事务**：一次提交（新区块、提交记录、空间指针）在一个事务里完成。
- **索引和迁移**：数据库地址是私有的，只有集群内能连，所以在接口服务启动时执行。
- **容量**：数据库占用不计入 chrono-cd 配额，但这是共享集群。扫描文件可能有几百 MB，需要先和平台团队确认容量预期和备份策略。
- **可替换**：大文件存储做成一层接口。如果平台不希望在共享数据库里放大文件，可以换成对象存储，比如用 NyxID 服务账号访问 chrono-bucket；业务代码不用改。

## 14. 部署（chrono-cd）

- **位置**：部署在 ChronoAI 组织下（个人配额 2 核 / 4G 太紧；组织默认 8 核 / 16G / 40 个容器 / 80G）。
- **项目和应用**：项目 `metaverse`，应用 `chrono-metaverse`，主机名由创建结果决定（新应用在 `apps.nyxid.ai` 下）。

| 服务 | 镜像 | 路由 | 暴露 | 说明 |
|---|---|---|---|---|
| `web` | `ghcr.io/chronoaiproject/chrono-metaverse-web` | `/` | 公网 | 静态网站 |
| `api` | `ghcr.io/chronoaiproject/chrono-metaverse-api` | `/api` | 公网 | 健康检查 `/api/healthz`；挂 MongoDB 插件 |
| `worker` | `ghcr.io/chronoaiproject/chrono-metaverse-worker` | — | 内部 | 从任务表领任务；内存限额 4–8G |
| `render` | `ghcr.io/chronoaiproject/chrono-metaverse-render` | — | 内部，只允许 `api` 访问 | 无头浏览器出图（没有 GPU，用软件渲染） |

- **镜像要求**：只能用 ghcr.io，建议设为公开包；用数字形式的非 root 用户（如 `USER 1000:1000`）；构建 linux/amd64。
- **持续集成**：GitHub Actions 构建并推送镜像，再用 NyxID 组织 API key 调用 chrono-cd 更新镜像版本。
- **注册到 NyxID**：
  - 第 0 阶段：先在 ChronoAI 组织下自助注册自定义服务，指定 OpenAPI 地址，并开启身份令牌（`identity_propagation_mode=jwt`）。
  - 稳定后：请平台管理员注册成目录服务。这样所有用户自动可用，服务编号也是固定的。

## 15. 平台核查结论

| 项目 | 结论 | 对设计的影响 |
|---|---|---|
| chrono-cd 公网路由 | 直接暴露，前面没有 NyxID | 写接口自己校验身份令牌（9.1） |
| chrono-cd 与 NyxID 注册 | 不会自动注册 | 手动注册（14 节） |
| chrono-cd 镜像 | 只能用 ghcr.io；用户必须是数字 uid | 见 14 节 |
| chrono-cd 超时 | 负载均衡 300 秒；前面的 Cloudflare 约 100 秒 | 耗时操作做成异步 |
| MongoDB 插件 | 共享 Atlas、MongoDB 8；不计配额；文档里没写备份 | 向平台确认备份和容量 |
| NyxID 身份令牌内容 | 有用户编号、全局角色、权限、服务编号；没有 key 或 agent 信息 | 空间钥匙负责留痕（9.3） |
| NyxID 角色 | 全局；自定义角色只能由平台管理员创建 | 空间级权限在本服务内实现 |
| NyxID 按接口限制 key | 有，但默认关闭、只能人工配置、不支持通配 | 不依赖它 |
| NyxID 代理头 | 白名单，自定义头会被丢掉 | 参数放路径、查询参数或请求体（8.4） |
| NyxID 请求体 | 100MB，经 AI 工具约 75MB | 分片上传 |
| NyxID 生成 AI 工具 | 按 operationId 命名；二进制转 base64；小图片可以直接返回 | 截图接口返回 PNG |
| chrono-bucket | 需要 `chrono-bucket-user` 角色（目前账号没有）；按版本号写入有覆盖问题；不支持分段下载；没有前缀列表 | 第一版不用，改用 MongoDB |

## 17. 待定事项

1. 空间是否都公开，还是需要"仅特定人可看"（那样网站就要接 NyxID 登录）。
2. 事件可见级别怎么划分（例：公开 = 营业状态、入座人数；内部 = 订单金额）。
3. 格子尺寸默认值：精细（5–10 厘米）还是方块感（25–50 厘米）。
4. 扫描格式：网格模型还是高斯点云。
5. 虚拟位置给谁用：内部和 AI，还是开放给合作方或顾客；他们能放什么。
6. 第一批数据源：收银、预订、摄像头、外卖……；摄像头事件服务是否属于这家餐厅。

## 18. 风险

| 风险 | 应对 |
|---|---|
| 共享数据库里放大文件，平台不同意或容量不够 | 大文件存储做成接口层，可以换成对象存储 |
| 没有 GPU，服务器截图慢 | 限制分辨率，缓存截图，只在需要时生成 |
| 扫描质量差（噪点、缺面） | 对齐可以手调，清理步骤，必要时由人或 AI 修补扩展层 |
| 钥匙注入的头可能被 NyxID 丢掉 | 备选方案：放在请求体字段里 |
| NyxID 令牌里看不到 key | 由空间钥匙留痕；同时向 NyxID 提需求，把 key 信息加进令牌 |
